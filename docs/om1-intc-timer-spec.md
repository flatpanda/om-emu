# OM-1 interrupt controller and timer block in the lab

Firmware = E143 v1.9 main block. Code addresses are disassembly notation (body offset + 0x50000000); data addresses run-time (body offset + 0x60021020). Tags: **X** executed in the lab, **D** read from the code, **I** inference, **?** unknown. Labels: A-* are assumptions, H-* harness choices; each is listed with its evidence in section 5.

## 1. Interrupt path, end to end

1. A device model drives a line: the OSD engine IRQ 310 = status & enable & 3 (`emu/src/dev/engine.mjs`), VSC channel c IRQ 46 + 2c = INTST1 & INTEN1 & 3 (`emu/src/dev/vsc.mjs`), timer channel n IRQ 137 + n = status bit & enable bit (`emu/src/dev/timer.mjs`).
2. The controller presents, per level L, the lowest-numbered high IRQ whose bank-0 level register is `1 << L` (section 2) and raises the CPU request while any level presents one.
3. The CPU accepts the highest-priority presented level L that its gate admits when PSW.IE = 1 and L < PSW.IM (ISA spec section 11): frame {u32 PSW, u32 PC} at SP - 8, IE 0, IM L, `(0x8a00) = (16 + L) * 4`, PC = `0x60030000 | IVAR_L` (`mem16[0x8000 + 4L]`).
4. The vector page at run-time `0x60030000` (disasm `0x5000efe0`) holds the level slots: level 0 at `0x5000f000` (stores into ROM `0x50000008/0c/04` first: not modelled), levels 1..6 at `0x5000f038/40/48/50/58/60`, each `jmp 0x50017d41` (D). `+8` is the NMI slot, `jmp 0x5000f0f4` (not modelled).
5. The kernel entry `0x50017d41` saves context (kernel spec section 9) and calls the level handler `kcb[88][PSW.IM]`; the level handler (level 5: `0x5002e68f`) loops on `v = (0x99200700 + 4L)`, calling `handler_table[v / 4 - 1]` (table `0xa32600c0`, CPU 0) until v reads 0, then rewrites its GxICR word (`0x5101` into `0x8954` for level 5) (D, X).
6. The exit dispatches the tasks the handler readied and returns with RTI (`0x50017e83`).

The IVARs, GxICR and `0x8a80` are low RAM in the lab; the firmware writes them in `0x5000f068` (called by reset at `0x500001ec`, a path the lab does not run; H-VECINIT runs it): IVAR low halves `0x0020/58/60/68/70/78/80` into `0x8000 + 4L` (D, X), `(L << 12) | 0x0101` into `0x8940 + 4L`, `0xaaaa` into `0x8a80`, and `mov d0,(0x801c)` with the last d0 `0x60030080` (`0x5000f0da`).

The controller is level-sensitive and keeps no edge state: the firmware drains by re-reading until 0 (D). The CPU request is "some level presents an IRQ" (A-INTC-LINE); GxICR in low RAM is not consulted, because the firmware writes ENABLE into every level's word at init (`0x5000f071..98`) and after every drain (`0x5002e6c9`).

Lab window `0x89a00000` (64 KiB, debugger reads and writes; a CPU write is an error; a CPU read returns the window's RAM like a debugger read and is not recorded, because the window is a ROM device): magic `INTC`, gate {mode, pc} at `+0x008` (H-IRQGATE: 0 off, 1 only at the gate pc, 2 anywhere), presented and accepted totals, the request, the presented-level mask, error ring, per-IRQ line bytes (`+0x1000`), bank-0 level registers (`+0x2000`), test lines (`+0x3000`), presented ring (`+0x4000`, 256 x {irq, level, pc, insns}), accepted ring (`+0x5000`, 256 x {level, pc, insns}). Doorbell `0x89a20000`: a CPU store of 1 from harness code applies the test lines (0 off, 1 high, 2 high until presented once); a test line on an IRQ a device model drives is refused. Test lines exist for check_irq and check_kernel 7b only. M10B (window version 2): pending bits per bank at `+0x060`, the request {bank, set, clear} at `+0x070` that a CPU store of 2 to the doorbell applies (`pending = (pending & ~clear) | set`; the bank registers stay CPU-only), the repeat count at `+0x02c`, and the xcpu ring (total `+0x07c`, ring `+0x6000`, 256 x {bank, value, pc, insns}) of the sets of banks 1..3.

**The inter-CPU path (M10B, D unless marked).** Init `0x5002ce4d` (boot caller `0x5000032b`; H-IPIINIT): `0x5002de2d` writes 256 entries of 64 bytes at `0xa325a998` (+0 = 63, +52 = 0), then `0x50053fcd(324, 2, handler, cpu)` for CPUs 0..3 with the handlers run-time `0x6004e85a`, `0x6004e985`, `0x6004eab4`, `0x6004ebe1` (= `0x5002d83a`, `0x5002d965`, `0x5002da94`, `0x5002dbc1`) and `0x50054012(324, cpu)` (X: bank-0 level `1 << 2`). Post `0x50035afd(d0 target, a0 run-time function, a1 arg)`: target >= 4 -> errlog `0x43006001`, -1; descriptor [target][(0x8050)] at `0x60092cd4 + 64 * target + 16 * core` = {u32 write index *, u32 read index *, u32 ring, u8 bit}; when (write + 1) % 32 equals the read index -> errlog `0x43006002`, -1 (31 usable entries, X); else ring[write] = {function, arg}, write index + 1, then the doorbell store; the body runs between `0x50053ebe` and `0x50053f07` (X, I10). CPU 0's handler `0x5002d83a`, per bit of `(0x99200808)`: 1 sets a flag (`0x50017a6b`), 2 walks 31 task slots, 4 runs `0x5002dcf0` three times, 8 / 16 / 32 / 64 drain ring [0][0..3] with `0x50035be0` / `0x50035c34` / `0x50035c88` / `0x50035cdc`, each `calls (a1)` with a0 = arg, read index + 1 (X for bits 8 and 32). The Super Control Panel (menu spec section 15) is the first GUI path that posts: `0x50aa9d43` posts `0x60acb193` (`0x50aaa173`) to CPU 2 and waits for CPU 2's reply `0x60acbfb7` (`0x50aaaf97`, sets `(0x600430e4)` pattern 1) through ring [0][2] and bank-0 bit `0x20`; CPU 2's side (task `0x200e`, loop `0x50aaa99e`, command 3 at `0x50aaaced..0x50aaad66`) is the stand-in S-CPU2 (section 5). Task `0x200e` is AUD_LEVEL_MONITOR in the name table (CPU 2 task 14; cores spec 8); "audio sequencer" below refers to its aud_seq code (D): the strings the code around `0x50aa9xxx..0x50aaexxx` loads are aud_seq ones ("AUD DEVCHG QW" `0x60dbeac7`, "[aud_seq_io_get_output_device] output_device = " `0x60dc05de`, loaded at `0x50aac0d0` by the output-device getter `0x50aac0c6` = `(0xa33da774)`, "[command_rec_start]" `0x60dc0e40` at `0x50aadcba`, "mic_vol_level =" `0x60dc1253`); the reply word's getter `0x50aac0eb` = `(0xa33da778)` sits right after the output-device getter. ## 4. Lab clock and time mode

The lab clock (`emu/src/dev/timer.mjs`): one ns time line, owned by the machine and shared by the VSC (frame boundaries of running channels) and the timer (expiries of running channels). It moves only on the VSC doorbell's lab commands: ADVANCE(ns), RUN_TO_FRAME(c), and RUN_TO_EVENT(limit) (cmd 5, absolute limit in the debug window's ARG0/1): advance to the first event at or before the limit and latch every event at that time (sources reported at VSC debug `+0x030`, bit 0 VSC, bit 1 timer), or to the limit. Events at one time latch together, VSC before timer. Lab time never moves back: a source naming an event before the current time throws (a model bug; check_irq I7 starts its channels at 7,345,678 ns so that a channel whose t0 ignored the clock would be caught). With no timer channel running every pre-M9 command sequence gives the same time and latches (check_display, check_liveview, check_menu, check_nav byte-identical).

Time off (the default everywhere): H-TIMER as in M8 (vsc spec 9.5); no channel is programmed. Time mode (`MenuLab(time=True)`, `NavSession(time=True)`, `emu/bin/nav.mjs --time`): display start runs, in boot order (D: calls at `0x5002ccd7`, `0x5002cd7b`, `0x5002cd82` in the init task the lab replaces), H-BOOTTIME:

1. `0x5003121c`: IRQ 138..141 attached (level 5, CPUs 0..3), channel 0 RMW, channels 1..4 reload 999 and started, IE |= 0xf. Checked: channels 1..4 period 1,000,000 ns, IRQ 138 level 5 -> `0x50031198`.
2. `0x500642dd`: `(0xa32ca47c)` = `0x6034e190[0x50002fd3()]` = run-time `0x6011e0a0` (X), a table of 32 six-byte entries {u16 timer channel, u16 enable, u16 cpu}; index i holds timer channel i + 1 (D). `0x50064443` runs for each entry with enable 1: indices 4..31 = timer channels 5..32, 28 attaches through `0x50053fcd` (X). The firmware's own "channel" arguments (`0x50064323(ch, ...)`, `DisplayLab`'s M8 notes) are these indices.
3. `0x50058959`: the IRQs of timer channels 17..32 (indices 16..31) re-attached at level 3; the 2 ms software tick on timer channel 21 (index 20): reload 2000, started (period 2,001,000 ns under A-TMR-1/2; 2,000,000 ns if the firmware's own ms * 1000 is the exact period, see A-TMR-1 in section 5). Checked.

Then H-DEFER: task 16's init `0x5005304d` runs natively and its entry `0x500530f7` may start (static task table run-time `0x60039290`, D). Its caller `0x500248e2` in the boot function `0x500248b4` is not traced. Task 16 runs deferred calls; the Genifa timer's software slot callback `0x50ab8fe6` posts one (`0x50053505`), and the call (`0x510c1ccf`) advances the Genifa ms clock and wakes the Genifa timer task (kernel spec 9.5, X). Without H-DEFER the Genifa ms clock never advances (X, check_nav mutant `b7-no-task16`).

ELAPSE (`LabTask.elapse_until`, `MenuLab.elapse(ms)`, the nav token `WAIT:ms`, `NavSession` in `emu/src/lab/nav.mjs`): the lab task waits on its settle semaphore; at the idle point with nothing presented the harness rings RUN_TO_EVENT(target) and the CPU accepts what it latched there; at the target S-SETTLE signals the lab task. The kernel tick is then native: IRQ 138 -> `0x50031198` (ack, `isig_tim` `0x50011043`, `irot_rdq(55)` `0x50010f06` on every tick: the `inc; cmp 1; bcs` at `0x500311b0..b9` never skips) -> the exit's tick loop `0x50017ddd..0x50017e0c`. `settle()` never moves time; in time mode a timed waiter is logged, not an error. The idle hook syncs the presented ring into the harness's log at every pass, because an idle ELAPSE presents about 1.5 IRQs per lab ms (kernel tick, software tick, vsync) and the ring holds 256 (before M9's last changes a `WAIT:200` overflowed it at the next step; check_kernel 5c now waits 300 ticks and checks every presentation is logged). More than `idle_again_limit` (1000) consecutive clock moves with nothing presented is an error, not an endless loop inside one hook stop (check_kernel 5c, timer IE cleared). `NavSession` runs a `WAIT:ms` as ELAPSE slices of at most 10 s, one harness call each, because one call is bounded by `MenuLab.INSN_LIMIT` (200,000,000 instructions) and idle lab time costs about 3.8 million instructions per lab second (`WAIT:60000` as one call stopped with trap 7 at 52.1 s); at a slice end the lab task wakes at the idle point and waits again, and the firmware's own counts do not change (check_nav 9 runs the 10.5 s wait with two slices and, as a control with `WAIT_SLICE_MS` 11000, with one: equal GESetEvent calls, interrupt acceptances and DOWN row; the second slice adds one 'time' and one 'signal' entry of the harness's own to the idle log). The step's GESetEvent and hook-stop budgets grow by 0.4 and 9 per lab ms: idle lab time makes Genifa send the GUI its periodic message 0x0001 (GESetEvent from `0x510bb869`) every 10 ms, so a fixed per-step budget turned any wait over about 8.1 s into a false event storm.

Known limit (reported, not hidden): inside display steps the stand-ins still move the clock (vsync waits RUN_TO_FRAME, OlyTaSS as A10 ADVANCE) without servicing the timers, so their periodic channels count overruns there and those ticks are lost (X: 201 overruns on channels 1..4 and 100 on channel 21 by the end of a TFT bring-up at lab time 202 ms). A display step the firmware runs during ELAPSE can end past the target ('past' in the idle log). Within such a frozen stretch the order of a latched tick and the firmware's own work is set by where the CPU next looks at interrupts, not by time: in check_nav N3T the 2 ms tick pending at lab time 202,191,650 ns was taken inside the Genifa timer's create (`0x50058edf`, called with the callback `0x50ab8fe6`; the observer at its entry fires first) until 2026-10-24, when PER_SCPU's start at the store init began creating its 100 watchdog through the same service (`0x5005899c` type 2 -> `0x50058edf`, from `0x5005b8bf`) at the same frozen time: the tick is now taken in that earlier create's masked section (`0x50053ebe` .. `0x50053f07`, I: an interrupt mask and its restore), so the Genifa slot, created later at the same lab time, misses it, its count at the B7 bracket is 4 instead of 3, and every Genifa event, nav#4's last composite with it, comes one 2.001 ms tick later (X: the tick ISR `0x50058ffc` runs at the same lab times in both trees, 202,191,650 ns and on; only its order against the Genifa create changed). Not a bug of the link: on the camera the tick would be serviced when it falls due, and the Genifa slot's phase against the tick is arbitrary.

B7 natively (check_nav N3T, menu spec 13.7): after the popup OK the GUI awaits 0x9ac6 (`(0x603710f8)`, set at `0x5115c64e`). The prediction uses lab state only: the Genifa timer's software slot (the active slot of `0xa32c5620` with callback `0x50ab8fe6`; count c at +20, period p at +8, X: p = 5), channel 21's next expiry t1 and period P, and timer 522's start value (100, observer of `0x5124f980`) and Genifa clock G0 (`(0x603679d0)`, + 10 per Genifa tick at `0x510c1cd8`, D). The event comes on the 10th Genifa tick after the start (X, observed; the comparison inside `0x510bb7df` is not decoded), so with d Genifa ticks since the start: `T_pred = t1 + (c - 1 + p * (10 - d - 1)) * P`. Measured: c 3, p 5, d 0, t1 404,202,000, P 2,001,000, T_pred 498,249,000 ns; at T_pred - 1 the GUI awaits 0x9ac6 with the clock at G0 + 90, at T_pred it took the event (clock G0 + 100) and closed the popup.
