# 8. Hardware evidence and what it unblocks

Part of [HLE gaps](../hle-gaps.md), which gives the tags, the address notation and the file
of every section.

None of these needs flashing, but the last row, which needs code run on a camera.

| Evidence | Unblocks |
|---|---|
| A console log of the camera's debug UART (`0x98700018`, "AM shell = SIODBG"), if the board exposes it (?) | the highest-leverage single item: the per-core boot order (4.6); `per scpu trace / gettx / getst / ver` give every SCPU command and reply size (4.7); `cam rapinput` and the cam_debug register and KEEP dumps (4.2); `mec info / prmout` (section 7); `isc`, `sys_callrequest_info` (4.6, 4.11) |
| The A53 console on ARM_UART1 (`0x9a500600`, 115200) | wireless: daemon order, ISC errors, the A53 power policy |
| An HDMI clean-out capture on v1.9 with defaults reset, into a sink with a known EDID | live-view geometry, colour and cadence (sensor seam A), A15, the HDMI mode choice, the HDMI overlay layout |
| JPEG and ORF files, a .MOV, and an image of a card formatted in the camera | capture (EXIF, maker note, thumbnails, ORF compression), movie (atoms, tmcd, audio), storage (FAT or exFAT, label, AU alignment, DCF folder name) |
| A logic-analyser capture of the lens mount contacts (the serial link plus the IRQ 60 edge lines) | the lens seam: wire protocol, real lens data (ID, FuncFlag, MAG_CNG) |
| A capture of the IS unit's serial link | IS beyond BC_EXEC |
| Board photos (IMU, eye sensor, PMIC, sound IC) | the accelerometer register map, the eye sensor, the power manager, the sound IC |
| Battery AD readings against the battery indicator | the power manager's scales |
| USB descriptors and usbmon captures (MSC, MTP, PTP) | the USB data path |
| A Wi-Fi capture of an OM Image Share session; a BLE capture | the JS A53 service; BLE GATT |
| Timing: VD period per mode, shot-to-card, S2 to rec view, key latencies | the time model; completion times at the capture and storage seams |
| Photos or video of the rear screen: rec view, AF frames in S-AF / C-AF / tracking, the recording screen with audio meters, Connection Setup | checks for the capture, AF, movie and wireless displays |
| A dump of store F (flash `0x400a0000`, 128 KiB) | per-unit adjustment values, for a full boot |
| **Needs code run on a camera** (a patched build that copies memory to the card): a still's development job from an OM-3 (E147), for one COLOR shot and one shot in another picture mode, taken at the stage wrapper's entry `0x504f8e1c` (before the YC packing) and again after the stage list `0x504f8694` returns (`0x504f8e2e`); a second entry, `0x504f8e43`, calls the stage list first (at `0x504f8e44`) and `0x504f3088` after it (D), and which of the two a still takes is not read (?), so a dump is taken at both. The job record C (192 bytes, a0); the request R (C+4; 4 KiB covers every offset read so far, the highest R+1941 in 4.3.12's read sets); the register image (C+8; 16 KiB: the stages' output O is its +2832 or the request's own block, the second block follows O at +4396, and the set-up's dispatch hands out parts of the image up to its +11860); and after the call the tables O points at (the pointers at O+3172..O+3184, O+3828 and O+4344..O+4392; 32 to 4096 entries each). The offsets are 4.3.12's and 4.8.13's ("The development's pages"). A dump stays out of the tree and is read at run time, as a Caduceus checkout is; it may hold a body's calibration, so its owner decides what to share | the stage checks from "an assumed job" to "a camera's job": the lab calls the still's stages on a job a test writes (`emu/test/test_stages.mjs` under A-STAGEJOB, `emu/test/test_lookhooks.mjs`, 4.3.12), whose pinned read-while-zero lists say which bytes the dump must hold (E147: 117 for the stage list, 37 of them changing an output), and no call can show that the camera's request holds what the test wrote or 0 where the test left 0. One dump gives R's fields the stages read, whether the request names its own block and so which flags the stage list gets (C+60), the unit masks a development request sets (the image's words 0 to 2, 4.8.13) and a stock output to compare with, without the native TAKE, white-balance and parameter-set work of 4.3.13. It is E147's layout and says nothing of another body's |
