# 4.10 USB, PTP and PictBridge

Part of [HLE gaps](../hle-gaps.md), which gives the tags, the address notation and the file
of every section.

- **Tasks (D):** PC_EVENT 0x5d, PC_HOSTCOM 0x5e, PC_PCMRECLINK 0x5f, PC_PTP 0x60, PC_UAM 0x61, PC_USB 0x62 (queue 0x3c),
  PC_USBSRV 0x63, PC_PD_COM 0x7f (queue PC_PD_CMD_EXEC 0xcf; already runs 28 instructions, X), PC_CHECK_ALIVE,
  PC_HOST_ASYNC; PTP: PTPCOM 0x3c, PTPASYNC 0x3d, TPC 0x24, TPC_DATA 0x25, TPC_CAMC 0x04, TPC_LANG 0x3e,
  TPC_CAMC_FILEADD 0x71, TPC_STAMODE_MAIN 0x82; PictBridge: SAICAS and DPS_MAIN 0x0c (the DPS transport).
- **Device controller (D):** register-dump strings at `0x51026af8` name a Synopsys DWC_usb3x device core at
  `0x9a600000` (global registers `0x9a60c100..`, device `0x9a60c700..`, endpoint commands `0x9a60c800..`); glue
  `USBTOP_*` at `0x9a620000` and `0x9a610000`; IRQ 223 (level 5), handler `0x5102a9ad`, attached in PC_USB's init.
  Modes: storage, MTP, PTP, PC host SCSI; no UVC / UAC strings.
- **Events (D):** EV_USB_CONNECTED 8 / DISCONNECTED 9, EV_USB_RXDETECT 363 (code `0x040d00d2`), the USB select GUI;
  the power source and PD come from the SCPU (`usbSupplyType`, `POWERSOURCE_USBTYPEC`). Who posts EV_USB_CONNECTED,
  and the VBUS source (ADC flag `0xbf`, I), are ?.
- **Size of the data path:** mostly PTP (TPC, about 52.6k) and PictBridge with its XML parser (about 89k in parts), not
  mass storage. PTP is also used by Wi-Fi station mode: the Wi-Fi API calls `tpc_station_mode_get_param` (D), the
  hand-off from PTP-IP is ? (I: a shared PTP layer).
- **Seams:** the event level first (connect, disconnect, the select screen, charging state), then a class level (the
  PC_USB queue with a host-side PTP / MTP client), and only later the DWC3 device model with the SD-USB link for MSC.

## 4.10.1 The cable at the event level (2026-11-22)

- **The producer (D, X):** on the E143 board the USB connection reaches the MN as the sub-CPU's port-scan report: PC13
  (GIO port 45) changing posts the message `0x08` {PC13} (the sub-CPU's `0x801a436` through `0x801271c`, 4.7, D),
  PER_SCPU's dispatch `0x5005d43e` hands bit 0 to UI_IN's group-4 producer `0x5014d537` as the switch `0x0400` (X,
  H-UIINSCAN's path). On the E144 family the same switch becomes the module event the application's broker gives
  CA_MAIN as event 8 OLY_USB_CONNECTED, followed by PC_START_PC_USB_SELECT (D, X; `src/lab/play.mjs`
  IDLE_SWITCH_STATES). The VBUS sensing behind PC13 on the board, ADC flag `0xbf`, the PD controller and the
  `0x14` / `0x40` power-source paths are not read here (?).
- **S-USBCABLE (`src/lab/play.mjs` usb_input, input `{type: 'usb', action: 'plug' | 'unplug'}`):** sets the sub-CPU
  model's PC13 and runs 1.5 s of lab time. S-TAKEOVER's guard lets `0x50abb01d` and `0x50b7a2de` read module 9 from
  the first cable step on (both plug and unplug read `0x50abb01d`, X); what state 2 means to them is I.
- **Result (X, E143, `emu/test/test_usbcable.mjs`):** the plug's `0x08` {1} is polled (`0x8f`) and UI_IN decodes
  `0x02020400`; the GUI stays at `0x0108` (SS_COMMON / ID_ST_CA_REQ_DISP) and no USB select screen is drawn within
  1.5 s. The unplug decodes `0x02020400` again and leaves the GUI at `0x0108`. So on E143 the switch code alone does not
  reach EV_USB_CONNECTED: the step from `0x02020400` to event 8 (whether E143's shooting service publishes the switch
  as the E144 family's does, or a PC_* task posts it after the PD / power-source notice) is ? and is the next read.
  Not run: EV_USB_RXDETECT 363 (`0x040d00d2`), PC_USB's init and IRQ 223.

## 4.10.2 PC13's polarity, the code's consumers and the way to the select screen (2026-11-23)

- **PC13 is active low, so the lab's sessions start with a cable in (D, X).** The sub-CPU's scan keeps PC13's raw level
  in bit 0 (`0x8012828..0x801289a`) and hands the power manager message 10 with the level inverted (`0x80126a2`); its
  handler `0x801a436` sends the MN `0x08 {0}` for PC13 low, with `0x8015d44(1)`, and `0x08 {1}` for PC13 high, with
  `0x8015d44(0)` and `0x801acb0(1)` (D). PC13 low also wakes the sub-CPU from standby as WKUP2 into bkground
  (`test_stm32l4.mjs`, X) and selects bkground at a power-off, where PC13 on its pull-up leads to standby (4.7, D). On
  the MN, bit 0 is the producer's value: 0 puts `0x0400` at state 0, and the application's USB test `0x50abb032`
  answers 1, connected, for state 0 (`0x50424f9a(0x02020400) == 0`, when module 9 is neither 1 nor 2), D. So
  S-SCPUDEV's SCAN_IDLE (PC13 low) is a cable in, and S-USBCABLE's plug, which raised PC13 until today, was the
  removal. S-USBCABLE now follows the polarity: the cable starts in (the model's PC13), the first step is an unplug
  (PC13 high), a plug drops PC13 (`src/lab/play.mjs` usb_input).
- **Two consumers of `0x02020400`, both gated by module 9 (D, X).** The application's code dispatch `0x50abbae9` asks
  the handler's vt+12, the filter `0x50abafce`, and only on 1 calls vt+16 (`0x50abbaf7..0x50abbb12`). The filter returns 0
  for `0x02020400` when module 9's state is 2 or 1 (`0x50abb00e..0x50abb02e`); the handler (`0x50abb2d7..`) then calls
  `0x50abb032` and posts event 8 OLY_USB_CONNECTED (`0x50b7a392(8, 0)` at `0x50abb32b`, after 13 when HDMI and the
  word `0x50ab4e0f` read 0) or event 9 OLY_USB_DISCONNECTED (`0x50abb34c`, after `0x50ab47c8(0, 0)` and
  `0x50ab47c8(1, 0)`). The second consumer `0x50b7a2c4` makes the same module-9 test (`0x50b7a2de`, `0x50b7a2ee`) and
  then reads the switch and `0x5040dad7`. In a default play session S-TAKEOVER's state 2 ends both at their first
  read (X, E143, `emu/test/test_usbcable.mjs`: unplug and plug each decode `0x02020400` and read module 9 at
  `0x50abb01d` and `0x50b7a2de` only, the GUI stays at `0x0108`). E146 and E147 read at their ported places and stay at
  `0x0108` too (X).
- **Under control camapp 3 the event reaches CA_MAIN (X, a probe; module 9 is the components' 0 there).** A session
  started at PC13 high (the lab's idle image and UI_IN's group-4 image and old state set to state 1 before UI_IN's
  start, so the scan decodes nothing) took PC13 low as event 8: the handler took `0x50abb32b`, CA_MAIN's lookup
  `0x51049f69` got `0x01060000` OLY_USB_CONNECTED (the {code, name} table at `0x512f1080`), and the shooting state's
  entry for it (row `0x512e4048`: `0x01060000` -> `0x51065a27`) ran. PC13 high again gave event 9 and `0x01060001`.
  Further readers of module 9 on that path: `0x50abb028`, `0x50d78459`, `0x50d78469`, `0x50b7a2ee` (X).
- **The handler waits for a USB host (D, X).** `0x51065a27` goes on only when `0x5105160c(0)` returns 1, and with no
  IC recorder, `(0x60366138)` 0 and the USB state API (65801) 0 that is `isCommunicateUsbDevice` (API 68118,
  `0x50b02799` -> `0x50abb5bd` -> `0x5040dad7` -> `0x5102b555`): the USB driver's state halfword `0x62b2d9f4`, which
  `0x5102b555` refreshes by a synchronous command 8 to the queue whose id is at `0x60043362` and which must be 1
  (D). No task answers that queue in the lab (S-MODACK's E_OK, no data), so it read 0 and the handler ended (X).
  With `0x5102b555` answered 1 in a probe, the handler issued command 38, which CA's parameter trace `0x5105d291`
  names PC_START_PC_USB_SELECT (case 38, `0x5105d4e4`), and within 3 s the GUI went to `0x0105` ID_ST_WARNING with
  "One Moment" on the TFT; CA_MAIN then took SUB_APPCHG_PC `0x08000007`, CAM_END_COMPLETED `0x06000000` and the
  media events `0x01080000`, `0x01080001`, `0x01080004`, and the screen stayed there for 10 s (X). What the PC
  application waits for there (a PC_* task, PC_USB's own answers) is ?, and the next read. An unplug from that
  state reached the settings' flash save `0x50af6a15`, which S-FLASHSAVE refuses (X).
- **Why the idle level stays low for now (X).** With PC13 high at the start (no cable), the lever's off makes the
  application call OlyHfwPower's startShutDown itself (`0x50af654b` from `0x50abe7e0`, CA_MAIN's return addresses on the stack, a scan),
  inside the lever's step and before S-SHUTDOWN's listing of its flash save, and S-SHUTDOWN's own shutDown then calls
  it a second time; with the cable in it is called once, by S-SHUTDOWN (X: the lever's off on E143 both ways). So the
  phantom cable is what keeps the application from its own shutdown, and the no-cable idle needs H-POWER /
  S-SHUTDOWN reworked to follow the application's shutdown (and the sub-CPU then ends in standby, not bkground).
- **Not done:** the select screen. Open, in order: the idle at PC13 high with the power-off rework above (done,
  opt-in: 4.10.3); a named
  stand-in or the PC_USB task for the driver state behind `isCommunicateUsbDevice` (what the host's enumeration sets
  there is I); what the PC application waits for after "One Moment"; the default session's module 9 at 2.

## 4.10.3 A session with no cable: the application's own shutdown followed (E143, 2026-11-24; X unless tagged)

- **The no-cable idle (`usb_idle out`, `OM_USB_IDLE=out`; `src/lab/play.mjs` USB_IDLE).** The sub-CPU's model starts
  its port scan at PC13 high: S-SCPUDEV's scan levels, or with `OM_EMU_SCPU=native` the board's drive of PC13
  (`scpum4.mjs`), from the session's start (`menu.mjs` store_init). UI_IN's module init (H-UIININIT) takes the level
  from the scan's first report: group 4's image is `0060` against the default's `0040`, and the start decodes
  nothing. S-USBCABLE's first step is then a plug: PC13 low, `0x08 {0}`, `0x02020400` decoded, module 9 read at
  `0x50abb01d` and `0x50b7a2de`, the GUI kept at `0x0108`; an unplug back the same way (`test_usbcable.mjs`).
  Default stays `in` (below). Refused on a body whose UI_IN init does not run natively (E146, E147): there H-UIINSCAN
  decodes `0x0400` at state 1 against the lab's idle image, which keeps it at 0 (X, E146).
- **The lever's off with no cable.** In the lever's step the application calls the HFW's CameraCommon::shutDown
  `0x50afd2d7` itself, from `0x5107f160`, with mode 1 and reason 1. The bytes there are D:
  `0x5107f149..5e` loads the object, takes its vtable slot 2 (`mov (8,a1),a1`), sets `d0 = 1` and `d1 = d0`, and
  calls. The path reaches that call when `0x51054da7` or `0x5105f2b1` returns other than 1 (`0x5107f103..17`, D).
  Which of their reads follows the cable is ?; the same function calls with reason 11 at `0x5107f0ee` and 13 at
  `0x5107f13b`. shutDown then calls startShutDown `0x50af654b` once, from `0x50abe7e0` (return `0x50abe7e7`). With
  the cable in, no shutDown call comes in the lever's step, and S-SHUTDOWN's call is the only one. The decision is
  made at the lever, from the cable's level then: a session started `in` and unplugged follows the application's
  call too, and one started `out` and plugged does not, even though S-TAKEOVER's state 2 drops the cable's code in
  both cases. Reason 1 is API_SHUTDOWN_REASON_BUTTON, so S-SHUTDOWN's choice of BUTTON is the application's own
  value (D).
- **H-POWER follows that call (`src/lab/power.mjs` PowerOff follow).** On E143 4.10.2 saw startShutDown twice:
  once from the application, once from S-SHUTDOWN. With the cable out (USB_IDLE `out` or an unplug), the lab now
  arms the power-off's stand-ins before the lever's step: S-FLASHSAVE's listing of startShutDown's save, S-PWRLOG,
  H-SCPUPOLL, the end at the last write, and observers at shutDown and at startShutDown. startShutDown's entry comes
  from the facts rule `powerOff`, new key `start_shutdown`: the entry of the function that loads its trace. E143
  `0x50af654b`, E146 `0x50b01313`, E147 `0x50b0bba1`; E146 and E147 need their port re-run. After the step the lab
  makes no call of its own. It checks one shutDown and one startShutDown, then lets the lab task wait in lab time,
  as an idle slice, until the power-off's last write. Deadline: 10 s from the application's call. A second
  startShutDown is an error. Seen: the RAM log's save, 0x85 `{1, 0, 0}` answered `0585010001`, pin 102 polled low,
  127 in the request word, and the session closed. With PC13 high, S-SCPUDEV's 0x85 handler takes message 6 to
  standby, not bkground (D for the image's rule, `0x80163a3`, scpu spec 3.4). S-SHUTDOWN is listed only while the
  cable is in.
- **The sub-CPU's own firmware (`OM_EMU_SCPU=native`).** The power-off runs the same way, and the 0x85 is answered
  with `0585010001`. At the session's end, 0.15 s after the lever, the machine is running and not in Standby,
  whether the cable is in or out. Run 30 s further on its own clock after the session, it still enters no Standby.
  It spends its time around `0x800cdc4..0x800cdde` (the GIO read) and `0x80134c8..da`, and its console does not
  answer `sysctrl get`. Which state its system-control task took is ?, and the next read for the standby end.
- **Default kept at `in`.** Under `OM_USB_IDLE=out`, `test_c3power.mjs`'s power-off session passes 3 of its 7
  checks and its lever session stops (X). Under control camapp 3, the application's shutdown ends at the 10 s deadline with TRA 586 unanswered, as
  S-SHUTDOWN's did; the follow reports it with the error log's `0x43002002` from `0x5002bd72`. CmpSdw stays in
  state 3 in the control, not 5. The lever session without S-SHUTDOWN stops at S-FLASHSAVE, because the
  application's save `0x50af6a15` is not listed there. E146 and E147 have no no-cable idle yet (above), and the golden
  sessions were not run against `out`. With `in` the lever's off is unchanged: same record, lab time
  `2888127860..2998000000`, sub-CPU in bkground.
- **Not done:** `out` as the default (the c3power sessions and the golden first); E146 and E147's idle image with no
  cable; the native sub-CPU's end state; what `0x51054da7` and `0x5105f2b1` read.

## 4.10.4 The USB host behind the cable and the PC application after "One Moment" (2026-11-24)

- **The start with the cable out (X, E143).** The Player's `usb_start: 'out'` (set by tests) puts the sub-CPU model's
  PC13 high before UI_IN's module init (`src/lab/play.mjs` play_bring_up): its port scan (`0x88`) reads it, group 4's
  image and old state hold `0x0400` at state 1, the start decodes nothing and the GUI comes up at `0x0108`. A plug then
  posts `0x08 {0}`, UI_IN decodes `0x02020400`, CA_MAIN looks up OLY_USB_CONNECTED and runs `0x51065a27`, as 4.10.2's
  probe did. Under control camapp 3 the plug's path reads module 9 at `0x50abb028`, `0x50b7a2ee`, `0x50d78459`,
  `0x50d78469` and, past command 38, `0x50abe6f0` (X), which S-TAKEOVER's guard now lets through there
  (USB_CMP_MODULE9_READERS); each reads the components' 0.
- **The driver's state query and its receiver (D).** `0x5102b555` refreshes the state halfword `0x62b2d9f4` while it
  reads `0xffff` or the byte `0x62b2d9f6` is 0: it builds `{u8 cmd 8, u8 seq (0x5102b6f9), u16 state}` on its stack,
  sends it synchronously (`0x5002e39d`, `0x5102b585`) to the queue whose id is the halfword `0x60043362`, which holds
  207, PC_PD_CMD_EXEC (X; S-MODACK's queue, fact `api.pc_pd`), and stores the request's +2 halfword into the state
  (`0x5102b58c..0x5102b596`), 0 when the send's status is not 0. `0x5002e39d` passes the request's address in its
  message (+12) and returns the reply's first halfword, so the answer is written into the caller's request in place.
  The receiver is task 127, PC_PD_COM (entry `0x5102b2a4`, the static task record at `0x50018e94`): it receives from
  the same queue (`0x5102ba08`), dispatches commands 1..10 through the table `0x612b9818` (command 8 to `0x5102b7fa`),
  which hands the request to the sub-CPU as PER_SCPU command `0x40` (`0x5102b8f7`, the strings "PCPDC" and
  "USB SCPU_CONN" at `0x612b9804`), waits on the flag `0x60043134` for the answer written into the request
  (`0x5102b68e`, `0x5102b98a`), clears +2 on a failure and replies with the status (`0x5102ba37`). The init that sets
  the state to `0xffff` and `0x62b2d9f6` to 1 (`0x5102b23f`, from USTART5's `0x501ea586`) does not run in the lab, so
  every query sends (X: `0x5102b555` ran three times in the control's plug, each a send). In these sessions PC_PD_COM
  and PC_EVENT..PC_USBSRV (tasks 93..99) are dormant (X, state 0x10).
- **S-USBHOST (`src/lab/play.mjs` usb_host_install; the Player's `usb_host`, set by tests).** While S-USBCABLE's
  cable is in, command 8 from `0x5102b585` (checked by its bytes and the queue word's value) is answered E_OK with +2 =
  1; any other send stays S-MODACK's. The 1 is what `0x5105160c` needs (D); that a communicating host makes the PD
  side answer 1 is I.
- **Result (X, E143, `emu/test/test_usbselect.mjs`).** Control: the handler ends at `0x51065a27`, no command 38, the GUI
  stays at `0x0108`. With S-USBHOST: the state reads 1, command 38 PC_START_PC_USB_SELECT is issued (case 38 of
  `0x5105d291`) and the GUI goes to `0x0105` "One Moment" within the plug's 1.5 s.
- **What follows "One Moment" (X, the firmware's own trace calls `0x5108a4b6` with their strings, and CA_MAIN's
  lookup `0x51049f69`).** The shooting sub-app ends (EndProc, "CLEAR SHOOTING FUNC", endShootingService,
  completedEndProc, EndSubApplication), CA_MAIN takes SUB_APPCHG_PC and then CAM_END_COMPLETED ("CHANGE_APP"), and
  PC_APP (the object at `0x624586c0`, its strings "PcApp:...") starts its sub-app (constructor `0x510804fc`, strings
  "command PcCommon"): startInitProc, startPcModeSubAppStatePc (`0x51061b06`), checkPcMode, then startPc
  (`0x51061b50`): setUsbControlType and the camera API's connect (`0x50b408f2`), which runs the PC module's API
  `0xe0002..0xe0004` inline in the application's task (`0x503f06c0..0x503f0818` into `0x510228c2`, `0x51022792`,
  `0x5102285d`), among them one synchronous request to FILECLBK (queue 31, command 16, reply queue 55), which the
  native FILECLBK answers. Then the sub-app returns to its waitEvent. Nothing is posted to the PC_* queues 51..60 and
  no task waits on a reply (X: every task at its own wait); the events CA_MAIN takes afterwards (the media events,
  `0x01020001`) are refused ("CheckEvent:FALSE") or handled as "command PcCommon", and the GUI stays at `0x0105` for
  2 s more (X).
- **Not done:** the step out of "One Moment". Which event SubAppStatePc waits for after startPc is not read: its event
