## 4.3.9 The JPEG encode (2026-11-11; D unless tagged, addresses E143's)

- **Why.** S-JPEGENC stands in for the run and rec_ImgPro_Jpeg_Result (4.3.4). This round reads what the run asks of
  the hardware, to see whether the encode can be a request of its own that a device model answers. It is not one: the
  encode is a stage inside the image library's pipeline request, and the JPEG codec it starts holds no buffer address.
  The codec's block and its driver are read below; the pipeline unit around it is read in 4.8.13 (its protocol as the

## 4.3.15 REC_RAWNR's decision `0x5052acc1` (E146; 2026-11-22; D unless tagged, E146's addresses)

- **Why.** 4.3.5 left open what `0x5052acc1` decides in REC_RAWNR (task 32) before it runs `0x50518f3b` and
  `0x50520916`. The task does not exist on E143 (4.3.5: neither the name nor the queue in its image), so the reading
  is E146's; E147's copy is not read.
- **What it reads.** Its one argument is REC's packet (a0). It asserts the packet and its pExifParam (+20, the shot's
  record) are not 0 (`0x51a05155` with lines 2285 and 2286), then starts at 1 and clears to 0 when any of these holds:
  - the record's byte +7483 is 1 (`0x5052acfc`);
  - the packet's Mode (+186) is none of 4097, 4108, 4099, 4100, 4115, 4109 (`0x5052ad08`..`0x5052ad2e`);
  - `0x5052a12c(packet)` gives 1 and Mode is none of 4099, 4100, 4115 (`0x5052ad30`..`0x5052ad4e`);
  - the record's byte +38216 is 23 (`0x5052ad51`).
- **`0x5052a12c`.** For Mode 4108 it gives 1 when +38216 is 20; for 4099, 4100 and 4115 when the record's word +6140
  is 8. Otherwise it returns `0x5052a1e8(packet)`, which gives 1 when `0x5052a1fe` gives 1 or 3. `0x5052a1fe`: for
  Mode 4097 with +38216 22 it calls `0x508779f7(&w)` and, when that gives 0, returns 1 for w 0 and 2 otherwise (not
  read further); for 4099, 4100 and 4115 it returns 3 when +6140 is 11; else 0. REC_IMAGE's Mode 4097 call of
  `0x5052a1e8` (4.3.5) is this same function.
- **So for a normal still (Mode 4097)** the decision is 1 unless +7483 is 1, +38216 is 23, or +38216 is 22 with
  `0x508779f7` giving 0 and w 0. It reads no exposure time: the inputs are the record's +7483, +38216 and (other
  modes) +6140, and the packet's Mode.
- **The writers.** +38216 is a shot-kind byte that TAKE's code at `0x503bcf71`..`0x503bd0d1` sets from the shooting
  settings: 1, 11, 13 or 15, 14, 16, 19, 20, 21, 22, 23 on its branches (the six stores and the shared one at
  `0x503bd0d1`); what each kind means is ?. +7483 is stored at `0x5051f04e`, `0x5052384f`, `0x505287c8`,
  `0x5052b5ed` and `0x5087a0c3` (not read). Both found by a scan for `movbu` stores at those offsets in E146's main
  block (X: 6 and 5 sites).
- **The lab.** S-RECREQ still posts in REC_RAWNR's place on E146 and E147 (4.3.5), so the decision does not run and
  no test asserts it; S-EXIFPRM's template leaves both bytes 0, which would give 1 (the RAW NR branch) if it ran.
- **Open.** What `0x50518f3b` and `0x50520916` do (the RAW NR step itself), `0x508779f7`, the meanings of the shot
  kinds, the writers of +7483, E147's copy, and running REC_RAWNR natively in the S2 session.

## 4.3.16 camapp 3: who can call shutDown (2026-11-22; D unless tagged, addresses E143's)

4.3.6 and 4.3.10 left the camera's route from the lever's off to CameraCommon::shutDown open under camapp 3. This
round is static only (no session run, the user's instruction for the round): a scan of E143's main block for every
direct call (`call` d16/d32, `calls` d16/d32, relative targets) of the power-off chain and for every data word that
holds one of its run-time addresses (image base `0x60021020`). Nothing in the lab is changed; S-SHUTDOWN stays the
only way in under both camapps, and 4.3.6's PowerError at TRA 586 is unchanged. The light check (a camapp 3 lever's
off ending at H-POWER's last write) is not met.

- **The chain's callers (D, the scan).** shutDown (`0x50afd2d7`) has no direct caller; its one data word is the
  CameraCommon vtable's slot 2 (run-time `0x60e02eac`, code notation `0x50de1e8c`, vtable `0x60e02ea4`). Its inner
  call `0x50abe7e0` has one caller, shutDown's `0x50afd31f`. startShutDown (`0x50af654b`) has two, `0x50abe7e0` and
  the factory reset's `0x50af96d2` (4.7.4). api_system's power-off `0x5041fa85` has one, startShutDown's
  `0x50af6e19`. `0x50044ca8` has 4.7.4's callers: `0x5041fad9`, the firmware update's `0x51034f23` and three in
  code still not read, `0x5180799a`, `0x519d0348` and `0x519d9be9`. So, short of those three and the factory reset,
  every native power-off goes through slot 2 of the object the getter `0x50afccd5` returns.
- **The getter's callers (D).** 938 direct calls: the shell and HFW range `0x50afae61..0x50b38fe9` and the
  application `0x5108bf9d..0x51287c34`; none in the HLS range (`0x50b39000..0x51034f23`), so neither
  CmpCCom_CameraCommonComponent (`0x50d034a8..0x50d05ef3`) nor CmpSdw_ShutdownComponent (vtable `0x60eee834`) calls

  call (it is I at most, through a stored object). In the disassembly of both ranges (objdump, `tools/mn10300dis.sh`'s

  wrapper that returns it (one candidate: `0x5108bf9d`, a getter call followed by `ret [a2],12`, its callers not

- **What this leaves (D, I).** The HLS (sequence parts, CmpSdw) does not reach shutDown itself; under camapp 3 the

## 4.3.17 The E143 family's DRAM from MM's bank 0; S-RAWFRAME by default (E143, E146, E147; 2026-11-23; D unless tagged, each body's addresses)

- **MM's bank 0 in MM's init.** Each bank's pool is constructed by `mov POOL,a0; mov BASE,d0; mov BLOCK,d1; mov
  HANDLE,a1; call` (the handle the bank << 8). Bank 0's (E143 `0x50533ba4`): pool `0xa31f4e9c`, base `0xb8000000`, block
  `0x1ffec00`, `mov 0,a1`, `call 0x5053733b`, with the stack arguments 99 at (4,sp), the second region `0x08000000` at
