# OM-1 inputs in the lab: keys, dials, switches, touch

Firmware = E143 v1.9 main block. Code addresses are disassembly notation (body offset + 0x50000000); data addresses run-time (body offset + 0x60021020). Tags: **X** executed in the lab (the check or script is named), **D** read from code or data at the cited address, **I** inference, **?** unknown. Stand-in labels (H-*, S-*, A-*) are listed in section 8.

## 2. UI_IN (static task 84)

**Task and init.** Entry `0x5014b736`: wait on its event flag (id at `0x60043010`, `0x5002bdd8` with pattern 1), clear it (`0x5002bedd`), process the key ring (`0x5014c763`), run the dial step (`0x5014b895`), loop (D). Its module init `0x5014bf91` is part of boot and does not run in the lab: it stores 0 into `0xa32dab3c` and `0xa32daba4` (both already 0 in the lab's BSS), calls the ring init `0x5014cb5f` at `0x5014bf9e`, then `0x5014e3ab`, `0x5014ce00`, `0x5014d49e` (group 4's image, section 3), `0x5005d36a`, `0x5014d62e`, `0x5014d97a` (the others not traced) (D). H-UIINRING runs only the ring init, then H-UIIN starts the task with `act_tsk(84)`.

**The ring.** `0x5014cb74(d0 bytes, d1 group, a0 data)` appends a 7-byte record at the write pointer `(0xa32dab9c)` and advances it by 7, wrapping from past `0xa32dab93` to `0xa32dab54`; the read pointer is `(0xa32daba0)` (D, `0x5014cb8f..0x5014cbbd`). The ring init `0x5014cb5f` sets both pointers to `0xa32dab54` (D). Without it both are 0 and the records are written to low RAM 0, 7, 14, ...: the M10 buttons investigation's probes ran that way, and in play it put `0x3c` into low RAM 0, the byte the panel I2C code reads through a null pointer (M9 follow-ups, I2C map init), so the next EVF open faulted at `0x5005e55c` (X). With H-UIINRING low RAM stays 0 (X).

**Groups (C3).** Five records of 12 bytes at `0x60224774` (read by `0x5014c05a`, `0x5014c817`, `0x5014cb07`, ...): {u32 variant list, u32 old-state address, u8 bytes, u8 bits per byte, u8 entries, u8}. The variant list holds one entry table per variant; an entry is 8 bytes {u32 code, u8 type, u8 polarity, u16} (D, image bytes). Entry i is byte i / bits-per-byte, bit i mod bits-per-byte. The variant index is `(0xa32dab38)`, set by `0x5014bf47` from the board byte (`0x50002fd3` reads `0x97f00254`) through `0x60224082`: board 0 -> variant 0, boards 1..7 -> variant 1 (D). The lab's board byte is 0 (S-BOARD), so variant 0; which board the OM-1 is, is not known (M6 follow-ups). Variant 1 moves some group-3 keys to other bits and adds CUSTOM6 `0x120b`; codes, EV names and GUI pairs do not depend on it.

`emu/src/lab/play.mjs` CONTROLS lists every entry with its group, byte and bit; Every play bring-up reads the key matrix from the image and requires it to equal CONTROLS (`apply_uiin_layout`).

**Decoding.** For each bit that differs from the group's old state, `0x5014c919(d0 code, d1 type, a0 polarity, a1 bit)` gives the code (D, `0x5014c919..53`): type 2 (a key) -> `0x02000000 | code` (press) when bit == polarity, else `0x02010000 | code` (release); type 1 (a switch) -> `0x02020000 | code` on every change, except the mode dial `0x1901`, which posts only when the changed bit equals the polarity (the newly selected position). The code goes to `0x5014c956`, which is not a plain pass-through (`0x5014c96c..0x5014ca77`, D): it drops the codes 0, `0xffa` and `0xffb`, and those at or above `0xfff0` go to `0x5014d2ad` only when `(0xa32dab3c)` > 0 (0 in the lab); for `0x2007` it re-registers the grip dials (`0x5014be4f`), for `0x121c` it calls `0x5014d537(0x2202, 1)`; and it sequences the shutter with the bytes `0xa32dada0/1`: a repeated S1 press is dropped, an S2 press with no S1 before it forwards an S1 press first, and an S1 release while S2 is held waits until the S2 release, which forwards S2 release then S1 release. Only `0x5014c3eb` forwards a code to `(0xa32daba4)` (its callers are `0x5014ca0d`, `0x5014ca52`, `0x5014ca72`; the forward `0x5014c402..1c`, D); that word is 0 in the lab, so it goes nowhere (buttons investigation, X). The player observes `0x5014c3eb` (the codes S-KEYMAP maps, X: F held, Space, F released, Space released forwards S1 on, S2 on, nothing, then S2 off and S1 off) and records the decoded codes at `0x5014c956` beside them. The decode `0x5014c919` and the post `0x5014c956` carry no long-press or repeat timing, and no long-press or repeat code comes from them (D, buttons §1). The module itself is not timer-free: it starts five software timers through `0x5005899c`: at `0x5014d15b` and `0x5014d1a1` with the callback `0x5014d173` (which starts itself again, 10 periods), at `0x5014d8d9` with the callback `0x5014d8e3` (a per-entry counter), and at `0x5014dc9a` and `0x5014ded5` (2 periods) with the callback `0x5014dcb2`, which sets or clears bit 0 of the flag whose id is at `0x60043174` (D). What they time is ?. The mode-dial position index is kept at `(0xa32daba8)` (X).

**Switch state.** `0x5014c015(code)` -> `0x5014ccdf` returns 1 when the old-state bit differs from the entry's polarity (D, `0x5014ccfc..0x5014cd08`). The touch driver asks it for the monitor `0x2402` (`0x501e4ba1`): 1 rejects touches ("TP7 TFT CLOSE"), so the monitor bit equal to its polarity 1 reads "not closed" (C2; X). In every lab before M10 UI_IN never ran and every old-state bit is 0.

**The mode dial's positions.** Asked for `0x1901`, the query `0x5014c015` calls the dial-index reader `0x5014c0de` (`0x5014c074..94`), which takes the position index `(0xa32daba8)` (255: none, answered 0), finds the index-th `0x1901` entry of the group (`cmp 6401,d2` at `0x5014c10b`) and returns the index-th word of the code table `0x602243a0`: 3, 4, 62, 53, 54, 55, 56, 10, 1, 2 for positions 0..9, then 0 (D). The build names the codes twice: the MODEDIAL_ pairs `{u32 code, u32 *name}` at `0x51a389fb` (P 1, A 2, S 3, M 4, B 62, UNDERWATER_WIDE 45, UNDERWATER_MACRO 46, I_AUTO 49, MOVIE 10, SCENE 39, SCENE_NAVIGATION 42, ARTFILTER 51, MY_MODE 19, MY_MODE1..4 53..56, NON 0) and the table `{u32 *name, u32 code}` at `0x6036518c` that the parser logging "modedial_to_code_tbl : MODEDIAL ENTRY ERROR" walks (the table added at `0x5100a99b`; NON 0, P 1, A 2, S 3, M 4, MOVIE 10, ..., MY_MODE1..4 53..56, no B) (D). So E143's positions 0..9 are **S, M, B, MY_MODE1, MY_MODE2, MY_MODE3, MY_MODE4, MOVIE, P, A** (D). The application takes the code as its mode (X, a play session stepping through all ten): the query answers each position's code, the HLS user-setting manager's changeMode (`0x50b7b17f`, "changeMode mode = %d, modeDial = %d") gets it as modeDial and logs SUCCESS (its transaction returns 0 under S-TRAACK), and the GUI's getModeDialState (the camera-common object's +80 method, called at `0x51251e1d` for the log line "getInterface()->getModeDialState() = %d") answers the API enum's value of the same name at every position: P 9, A 10, S 11, M 12, B 28, MY_SET1..4 15..18, MOVIE 5 (the enum's names and values are the "API_MODE_DIAL_* : n" strings from `0x50df18b6`). That MY_MODE1..4 are the dial's C1..C4 is I (by the names: the OM-1's dial carries P, A, S, M, B, C1..C4 and a movie position). The page names each position so (`emu/src/lab/play.mjs` mode_dial_names, fact `mode_dial` read by `emu/src/fw/facts.mjs` modeDial from any build: OM-1 II E146 has E143's ten; OM-3 E147's are S, A, P, MY_MODE5 63 (named by its modedial_to_code table only), MY_MODE4..1, B, M (D); a code a build does not name, such as E134's 62, shows as "position k"). The index is UI_IN's entry order. On E143 it runs P, A, S, M, B, C1..C4, MOVIE round the ten positions, wrapping between A and S, which fits a dial's ring, but where the positions lie on the body, which way the index runs and whether the dial stops at its ends are in neither the tables nor the reader (?): the lab steps the index modulo the count either way.

**Dials (C4).** The dial step `0x5014b895` reads up to five ring entries `{u16 value, u8 slot, u8}` at `0xa32daaf4` (indices `0xa32dab08/09`, count `0xa32dab0a`) and calls `0x5014bbb0(0xa32daab4 + 16 * slot)`, which publishes `0x02030000 | u16(slot + 12)` through `0x5014bbcf` -> `0x50025095` (call at `0x5014bc05`) only when the u16 at slot +4 is 1 and the u16 at slot +12 is not 0; the ring value is not passed on (D). A slot is 16 bytes: +0 u32, +4 enabled, +6 position, +8 the "+" counter, +10 the "-" counter, +12 u32 dial id (`0x02031902` main at slot 2, `0x02031903` sub at slot 3) (X: the slot bytes `06000000 0100 0100 0100 0000 02190302`). The ring's producer is `0x5014bc97(d0 value, d1 slot)` (D), and it has two callers, both counter writers (D): `0x5014bae6(d0 dial id, d1 signed delta)` finds the slot with `0x5014bb88`, adds a delta >= 0 to the u16 at +8 (`0x5014baf5..0x5014bb0b`) and the size of a negative one to +10 (`0x5014bb16..0x5014bb34`), moves the position at +6, pushes the ring entry (`0x5014bb4d`) and sets UI_IN's flag (`0x5014bb63..0x5014bb7e`); its caller is the command dispatcher `0x5100af66`. `0x5014bd60` reads the encoder position through `0x50059fa4`, takes a 10-bit wrapped delta with `0x5014bc15` and adds it to +8 or +10 by direction (`0x5014bdc0..cd`), then pushes it (`0x5014bdee`). These are the counter words the GUI reads for 59 / 60 (menu spec 13.3; S-DIAL in the nav harness writes them by hand). The player drives a detent through `0x5014bae6` (H-DIALSTEP, section 4): UI_IN posts the dial id natively and the GUI reads and clears the word (X: main +1 posts `0x02031902` and moves the Setup Menu from page 1 to 2; -1 sets +10 and moves it back; the dial script run against the nav harness's S-DIAL gives equal states and frames). The encoder position read `0x50059fa4` is not modelled, so `0x5014bd60` does not run; which physical dial is main and which rotation is "+" is ?.

**Joystick decoder.** `0x5014c12e(d0 code, d1 value)` is UI_IN's code entry (callers `0x504256c1`, `0x5100afb4..d1`, `0x518069e1`, `0x519da1d9`, `0x51a10afa/0d`, D). It sends `0x1234`, `0x1235` and the grip's `0x200e`, `0x200f` to the joystick decoder `0x5014ddee` (`0x5014c13a..56`, D), which turns the value into a 5-bit active-low byte (for `0x1234` the values 0..8 through the jump table at `0x602249b8`: four single directions, four diagonals, the centre; for `0x1235` 0 / 1) and runs the state machine `0x5014e1c1`, which posts through `0x50025095` (call at `0x5014e36d`), not through `0x5014c3eb` (D). Executed: `0x5014c12e(0x1235, 0)` posts `0x02001235` EV_PRESS_JOYSTICK_OK_KEY and `(0x1235, 1)` posts `0x02011235` EV_RELEASE_JOYSTICK_OK_KEY; `(0x1234, v)` posts `0x02021234` for every v 0..8. That code has no row in `0x60e48e60`: the camera application decodes the direction itself. Its code -> EV translation sends `0x02021234` (and `0x02021236`, `0x0202200e`) to `0x50b7a5a9` (`0x50b796c6..0x50b796e0`), which calls the query `0x50425355(0x02021234)`, returns when the answer is outside 0..8, and jumps through the run-time table `0x60e497dc` to `mov 369..377,d0`: 0 EV_JOYSTICK_UP_KEY, 1 DOWN, 2 LEFT, 3 RIGHT, 4 LEFTUP, 5 RIGHTUP, 6 LEFTDOWN, 7 RIGHTDOWN, 8 EV_JOYSTICK_RELEASE_KEY (`0x50b7a5a9..0x50b7a612`, D). Run natively after the injection, the query answers the injected v, and 8 after the centre (X). The decoder's byte table `0x602249b8` fits this geometry: opposite directions never share a bit and each diagonal is the union of its two neighbours (D). Going from one value straight to another without the centre leaves the decoder in the first direction, and the next centre posts `0x02001235`, a press (X, semantics verification), so the player sends one direction at a time and a second one through the centre (H-JSINJECT, section 4). The raw producer of `0x1234` / `0x1235` is ?.

## 3. Idle image and inputs (S-KEYBITS)

Group 0 has a firmware producer on E143, E146 and E147 since 2026-10-23 (H-SCPUPORT): the SCPU interface's port words, read by UI_IN's IRQ 320 callback, which pushes the port byte as group 0's record (`docs/hle-gaps.md` 4.7.2). The lab sets the ports' levels from group 0's image below; at bring-up the firmware's own init sets group 0's old state from them, so the idle image decodes nothing in group 0. What follows describes the other groups, and group 0 on the bodies without the port path.

The producers of UI_IN's raw bits (the SCPU's receive path, the poller) are not traced. S-KEYBITS keeps one image per group and pushes the whole image with `0x5014cb74`, then `set_flg(id at 0x60043010, 1)`; UI_IN decodes natively. Idle image: every type-2 entry released (bit != polarity; the three code-0 entries of group 0 too), every switch bit 0 (the old state of every lab before M10), except the monitor bit 1 ("not closed") and the mode dial one-hot at index 0 (the index-to-mode map is ?). Pushed once per group after H-UIIN; the codes it produces (releases and the switch changes 0 -> 1 of the monitor and the mode dial) go nowhere.

A switch bit of 1 is not neutral: group 4 all ones makes the menu close paint the black panel 6 (X, by bisection; menu spec section 15). The GUI's check is `0x50abaab7` (D): it asks `0x50424f9a` for HDMI `0x02020501` (from `0x50abaac5`) and `0x02020400` (from `0x50abaad8`, then `0x50ab4e0f`); panel 6 comes with both bits at 1 and with neither alone (X: group-4 images `0120` and `ffff` paint it, `0100`, `0020`, `fedf`, `ffdf`, `feff` and `0000` do not).

The switch state the firmware reads back is UI_IN's: `0x50424f9a(code)` -> `0x50425445` -> `0x5014c015` (called from `0x50425651`), 186 static callers, GUI code among them (D; it runs natively, X). With the idle image's LLPSW bit 0 (= its polarity) it reads as EV_PRESS_LLPSW (section 4).

**Group 4 has a firmware producer (H-G4SET).** `0x5014d537(d0 code, d1 value)` finds the code in group 4 only (`0x5014cd0b` searching from group 4, code & 0xffff), sets the entry's bit in UI_IN's own group-4 image `0x629887e4` to its polarity for value 0 and to the other level for value 1 (`0x5014d5a1..0x5014d5e7`), pushes the whole 2-byte image as a group-4 record (`0x5014cb74(2, 4, 0x629887e4)` at `0x5014d5f5`) and sets UI_IN's flag (`0x5014d606..0x5014d621`); it returns 1 for a code not in group 4 (D). Its callers pass group-4 codes only: the display driver's HDMI report `0x02020501` (value 0 when its argument is 1, `0x501d69c2..d8`), UI_IN's own LLPSW branch `(0x2202, 1)` (`0x5014c9a4`), the lens key `0x2202` and lens MF `0x02021519` (`0x502a7943..0x502a79e6`), the grip `0x2003` (`0x50044f29`, `0x50044f42`, `0x500456b3`, `0x5004574f`) and `0x0400` (`0x5005d45a`) (D). The module init `0x5014d49e` (not run) sets the image and group 4's old state to the polarity bits (D); in the lab both are BSS 0, the S-KEYBITS idle image of group 4 too. The player drives every group-4 input through this producer, so group 4 has one image. Before, S-KEYBITS kept its own group-4 image, and UI_IN's LLPSW branch pushed the firmware image (HDMI bit 0) over it: with HDMI toggled on, an LLPSW press made UI_IN forward `0x02020501` again (a second 121), the next HDMI toggle decoded nothing, and a lens-key press re-reported HDMI too (X, behaviour verification; with H-G4SET HDMI, LLPSW, HDMI, HDMI, LLPSW, LLPSW, lens key each report only themselves, X, and without it, the no-g4set mutant, they do not).

A key press sets its bit to the polarity and pushes the group; a release sets it back. The shutter button stands at the furthest stage a held key asks for (F half, Space full; I: a two-stage button): its S1 bit changes before S2 on the way down and after it on the way up, and releasing Space while F is held leaves S1 pressed (X). A switch toggles its bit. The mode dial pushes the one-hot image of the new position; the page sends relative steps for PageUp, PageDown and its arrows, so quick presses each move one position (X; the page's self-test, `?selftest=1`), and the absolute position for a pick on its ring.

## 4. Code -> EV -> GUI (S-KEYMAP)

**The firmware's tables.** The camera application translates codes with `0x60e48e60` ({u32 code, u32 EV id} until a zero code; read at `0x50b793f4`) and the switch table `0x60e49560` ({u32 code, u32 EV a, u32 EV b} from `0x60e49560` itself until a zero code; `0x50b7951b..8d`), which takes a when `0x50424f9a(code)` answers 0 and b otherwise (`0x50b79579..8d`, D). `0x50424f9a` is UI_IN's switch state (section 3) and runs natively in the lab (X). EV names are `{u32 id, char *}` at body `0xdb2130` (D). The lever `0x02021223` is special: with property 15260 non-zero the application uses the switch table, where it reads as EV_POWER_SW_ON/OFF (`0x50b794f9..0x50b79517`, D) (I: the "Fn lever as power switch" option).

**The pairing rule (I, mechanical).** `EV_PRESS_<K>[_KEY]` and `EV_RELEASE_<K>[_KEY]` pair with the GUI messages `EVT_KEY_<K>_ON` / `_OFF` (names at `0x6159a3a4`) and with `EVT_KEY_<K>_LONG_ON` where it exists; DEL is DELETE. `EV_PUSH_CEC_<K>` pairs with `EVT_KEY_CEC_<K>` (press only; the table has no release EV). The codes UI_IN posts itself pair by name too: EV_PRESS_JOYSTICK_OK_KEY / EV_RELEASE_JOYSTICK_OK_KEY -> 244 EVT_PRESS_JOYSTICK_OK_KEY / 257 EVT_PRESS_JOYSTICK_OK_KEY_OFF, EV_CHANGE_MAIN_DIAL `0x02031902` -> 59 EVT_ST_CHANGE_MAIN_DIAL, EV_CHANGE_SUB_DIAL `0x02031903` -> 60. Switches pair by explicit rows: mode dial `0x02021901` EV_CHANGE_MODE_DIAL -> 58 EVT_ST_CHANGE_MODE_DIAL, lever `0x02021223` EV_CHANGE_LEVER_SW -> 206, monitor `0x02022402` EV_MONITOR_LIFT_STATUS -> 207 EVT_ST_CHANGE_MONITOR_LIFT, rotate `0x02022401` EV_MONITOR_ROTATE -> 65 EVT_ST_CHANGE_TFT_ROTATE, monitor joint `0x02022403` EV_MONITOR_JOINT -> 208 EVT_ST_CHANGE_MONITOR_JOINT, headphone `0x02021711` EV_EXTERNAL_HEADPHONE -> 209 EVT_ST_CHANGE_EXT_HP. Two switches are only in the switch table: S-KEYMAP calls `0x50424f9a(code)` natively when UI_IN forwards the change and takes the EV the table's pick gives; LLPSW `0x121c` EV_PRESS_LLPSW / EV_RELEASE_LLPSW pairs with 66 EVT_KEY_LLP_ON / 67 EVT_KEY_LLP_OFF (I; from the idle bit 0 the toggles post 67, 66, 67, X, scenario `keys`), HDMI `0x0501` EV_HDMI_CONNECTED / EV_HDMI_DISCONNECTED with 121 EVT_ST_CHANGE_OUTPUT_HDMI (I). Toggling the joint, headphone and HDMI switches from the menu and from the shooting screen posts these indices without a fault and without a visible change (X). The rest is decoded only, for one of two reasons: the code has no EV name at all (`0x1229`, `0x2007`, `0x1506`, `0x1518`, `0x1712`, `0x2006`, `0x0400`), or its EV name has no GUI message by the rule and no explicit row is chosen (CUSTOMn, the grip and lens keys, EV_LENS_MF_SW_ON/OFF, EV_CEC_POWEROFF, EV_GRIP2_DETECT; what the camera application makes of them is ?).

## 5. Touch driver (task 83)

**Bring-up.** H-TPINIT: the boot call of touch init `0x501e3dca` (from `0x50024ca6`, D) from the lab task, then `act_tsk` of the static task whose id is at `0x60042dcc` (83; entry `0x501e3eac`). H-TPSTART: TP_OPEN `0x501e40da(a0 = HFW callback, run-time 0x60b97e80, a1 = 0)` and the gesture mask `0x501e41d1(-> 0x11f1)`, every gesture bit the driver posts (touch investigation §3, X); the camera application's own start (HFW `startTouchPanel` `0x50b76d47`, `ctrlTouchPanelEvent` `0x50b76b93`) is not run.

**Pins (S-GPIO-TP).** The driver reads pins 48, 49 and 108 through `0x50002a35` (`(0x60025ff8[pin])` bit 4): `0x9b880e00`, `0x9b880e40`, `0x9b883e80` (D, table bytes). Level 1 is the only level at which it accepts a touch (`0x501e4858..79`, `0x501e4bbb..df`, D). The lab-stub page `0x9b880000` is opened in play only, with presets 0x10 at the three registers; what the pins are is ?.

**Registers (S-TPREG).** `0x501e4fc8` reads 11 bytes from slave 0x70, register 0x02 (`0x501e4f2a`) and parses (D): count = r[0] & 15; point 1 x = (r[1] & 15) << 8 | r[2], event = r[1] >> 6 (0 down, 1 lift, 2 contact), y = (r[3] & 15) << 8 | r[4], id = r[3] >> 4; point 2 from r[7..10] the same way; r[1] bit 4 is stored separately (`0x501e5067..72`). S-TPREG serves `{count, ev << 6 | x >> 8, x, y >> 8, y, 0, 0, 0xcf, 0xff, 0xff, 0xff}`: the second point as event 3 at 0xfff (no point, the bytes of the executed probes). The flip `0x501e44c0` with orientation `(0x60357078)` = 0 reports y = 599 - raw, so S-TPREG serves raw y = 599 - y (X: raw (300, 200) -> (300, 399); the no-flip mutant serves the raw y). After a lift the image keeps count 0, so the watchdog's re-read (`0x501e5218`) sees no touch.

**Interrupt (S-TPINT).** The pin-110 callback `0x501e5233` sets bit 0 of the touch flag (id at `0x6004306c`) with `iOlyEvSt` (D); the lab calls `OlyEvSt(flag, 1)` from the lab task after each new image.

**Gesture queue (D, X).** The driver delivers a gesture at once unless it is a PRESS or the queue index `(0x62a3ebc9)` is not 0; then it copies the gesture into slot `index` of a 5-slot queue (20 bytes each at `0x62a3ebe4`, the copy `0x501e4a04`) and increments the index, with no bound check (`0x501e487b..0x501e48b2`). A PRESS starts a 10-period timer `0x5005899c(1, 10, 0x501e478d)` (`0x501e48c2..0x501e48df`) whose callback wakes the task to drain the queue (`0x501e47b9..0x501e47f7`), which resets the index only when it reaches an empty slot (D). Gestures with no lab time between them never let the timer fire: three taps posted together overrun the queue, the sixth gesture is copied through slot 5, whose pointer word lies in the point storage at `0x62a3ec48`, and the store at `0x501e4a13` faults (X: three, four and six queued taps fault, two do not, behaviour verification). H-TOUCHGAP (section 7) starts every touch sample at least 20 ms of lab time after the previous one ended, so at most one more input falls into the 10 ms after a PRESS.

**Gestures (X, idle off).** The driver's timers run on lab time. Tap at (300, 200): PRESS (300, 200) 11.89 ms of lab time after the down sample, CLICK on the lift. Drag from 100 to 660 px in 16 ms steps: PRESS, 14 SLIDEs with increasing x, FLICK on the lift. Double tap (lift and second down 80 ms apart): PRESS, CLICK, PRESS, DCLICK. A 1.5 s hold: PRESS, then LIFTOFF at the lift with A-USLAB, CLICK with H-USCOUNT (`--us-clock reads`; the recogniser measures holds on the us clock); LONGPRESS (mask bit 128) never comes, with or without contact samples: its path is not traced (finding). Monitor closed: no gesture ("TP7").

**The gesture mask follows the screen's build, not the shown display (X).** The GUI sets the driver's mask when it builds the shooting screen: ctrlTouchPanelEvent `0x50b76b93` turns its enable flags into bits (`0x50b76b9f..0x50b76be1`, D) and calls `0x504252c6`, which calls TP_MASK `0x501e41d1` (stored at `0x62a3ebc0`, `0x501e41f2`, D). Built with the TFT shown it is `0x11f1`; built with the EVF shown it is `0x40`, DCLICK only, and then neither a tap nor a double tap gives a gesture (X). SWITCH (M8) does not tell the GUI, so after LV the mask stays the one of the build: started on the EVF and switched to the TFT, taps give nothing until the screen is built again (MENU, MENU through S-CAMSEQ Q2/Q1 gives `0x11f1` and PRESS, CLICK); started on the TFT and switched to the EVF, gestures keep coming. The page shows the mask in its status line and sends touches only while the TFT is shown.

## 7. Lab time for inputs (H-IDLE, gating)

The player (`emu/src/lab/player.mjs`) runs lab time in ELAPSE slices of at most 50 ms between inputs, paced to the wall clock (H-IDLE): the kernel tick, the 2 ms software tick, Genifa timers, GUI key repeat, B7 and the shooting screen's refresh all run. When the lab falls behind the wall clock it re-anchors (counted as dropped 'pacing re-anchored'), and the status line shows the pace, lab seconds over wall seconds across the last 200 slices. Gating (X, scenario `b7-gate`): while the GUI awaits an event (`(0x603710f8)` != 0, B7) a press, dial, touch or request is held and 10 ms slices run until the event is taken (at most 2 s; MENU right after a popup OK was held 100.1 ms of lab time); without the gate that MENU is an event storm (the no-gate mutant). A release is not held: check_nav N3T posts OFF messages in that state without a storm (X). Inputs run in arrival order (one FIFO), except that the inputs of one page run in the page's own order: the page sends each input as its own request, so two in flight together (the last move and the up of a flick, a touchpad tap's down and up) reach the server in either order (7 % of pairs in headless Firefox, review measurement); each input carries the page's id and a sequence number (cseq), the FIFO gives the page's inputs their places in cseq order, and one that overtook an earlier one waits up to 0.3 s for it (X, scenarios `queue` and `pace-wall`; an up sent before its down gives PRESS, CLICK). Key repeats from the host are dropped; a run of queued touch moves is coalesced to its newest, never past a lift or another input (scenario `queue`). H-TOUCHGAP: a touch sample starts at least 20 ms of lab time after the previous one ended. With lab time running it also starts at least the user's gap (the page's own timestamps, t_client, else the arrival times) after the lab time the previous sample started at: inside a contact (a move or up after a down or move) up to 2 s, between contacts (a down after an up) up to 0.32 s. The 0.32 s cap comes from the driver's double-tap window: with lab time off, a second tap whose down comes 287.0 ms of lab time or less after the first one's lift is a DCLICK, from 300.3 ms on a CLICK (X, taps with WAIT between them; where the driver keeps the window is ?). So a pair the user tapped closer than 0.32 s runs with the user's gap and the driver decides as on the camera, and a pair further apart runs at least 0.32 s apart, outside the window (a 0.4 s cap kept the latency flat for taps every 0.5 s on an idle machine but not with the checks running in parallel, so the cap sits just above the window). Measuring from where the previous sample started keeps the time spent on it from being counted twice: the first rule (every sample at least its arrival gap after the previous sample ended) let tap latency grow without bound (0.13 s to 2.6 s over 30 taps every 0.5 s), and the second (a new contact waits for the 20 ms floor only) lost 30 to 60 % of the gap between taps, so a third of the taps at two per second became double taps (behaviour verification and review: lift-to-down gaps of 219-370 ms of lab time for 420 ms of user time). Six taps sent together give six PRESS and no fault; a click held 0.4 s whose up waited behind a busy lab keeps about 0.4 s between its PRESS and LIFTOFF; 12 page taps every 0.45 s (0.37 s from lift to down) are 12 CLICK with at least 320 ms of lab time from each lift to the next down; 16 page taps every 0.75 s keep a flat latency; six page double taps (0.12 s from lift to down) are six DCLICK (X; the tap-floor-only mutant puts the floor-only rule back and gets DCLICKs among the 12 taps). A tap costs at most its hold plus 0.32 s of lab time: taps every 0.5 s need 0.8 lab s per wall s, which an idle machine gave (30 taps, 30 CLICK, 400-435 ms of lab time from down to down); when the lab runs slower, taps queue up (the same taps with four checks running in parallel: latency up to 5 s with a 0.4 s cap). `--replay` logs the lab time a touch sample ran at (after its H-TOUCHGAP slice) and the lab time the driver's gestures went to the GUI, and runs both there. A frame runs lab time on to the next frame boundary, so the replay publishes one only where its boundary does not lie past the next entry's lab time (where the session published, it does not), and otherwise later; publishing after every wait put inputs and gestures up to one frame (16-18 ms) late, and publishing what drew in a wait after the entry instead ran the next entry late the same way (a touch down, then the menu request at the same lab time: the request ran 16.7 ms late and the PRESS came 44 ms early). The frame a replayed entry shows can be one refresh earlier or later than the session's, since frames are published at other points (X: 3 of 108 entries of a 36-tap replay with lab time running; GUI states, lab times and gestures all equal; with `--idle off` every frame is equal: scenarios `power-replay`, `scp-replay`). Restart and power on or off are in the session log and replay where they were logged, so the inputs after a restart replay on the new session; an entry that needs a session when there is none is an error. A replay of a queued click, a hold across the menu request and eight page taps on the refreshing shooting screen gives the same gestures at the same lab times and every log entry at its logged lab time (X; the mutants touch-lab-ns-early, which logs the lab time before the gap slice, replay-frame-wait, which publishes a frame after each wait, and replay-no-limit, which drops the next-entry limit, all break it); a replay across Restart and a power cycle gives the same GUI states and frames (scenario `power-replay`); at most 8 queued detents per dial run (the newest), the rest are dropped and counted (scenario `queue`, `emu/test/test_host.mjs`). A dial detent whose counter word the GUI does not read is reported (`dial_unread` in the record, the page's status line), the word is cleared and the session goes on (X). After every `?sync=1` answer `/api/status` already shows the input's result (X). Malformed inputs (a body that is not a JSON object, an id that is not a known control name, a detent count that is not an integer, inf or nan, a token that is not a string, an unknown action, a switch value other than 0 or 1, a mode-dial position or step that is not an integer) are refused with an error and the session runs on; an input taken off the queue when the loop fails is answered with the error (X). Step records are numbered by a counter that trimming does not cut, so the touch records' S-CAFWD lists stay their own (X).

**The DISPLAY queue (S-DISPQ) and blocked sends.** Every transition of the shooting screen (MENU in and out, PLAY in and out, direct WB, the black screen, S1 closing the menu) makes the GUI's display manager send one asynchronous DISPLAY request: `0x503eb960` takes the queue id of its target 35 from the table at run-time `0x606214a0` (`0x88`, the DISPLAY queue, whose id variable is `0x600432d4`; `0x503eb9b2`, `0x503eb9e1`) and calls OlyQeWr(id, -1) at `0x503eba00` with a 16-byte DISPLAY cmd 18 message {6, `0xf00n0000`, 18, param} (D; X: one per transition, LV switches, taps and dials send none). So the messages stayed in the kernel's queue: 30 sends, 0 receives, and the 30th send blocked the GUI task in tsnd_dtq forever (stack `0x50016734` <- `0x5002c1f8` <- `0x503eba07`); every later input did nothing, dials reported dial_unread, and the status still said running (X, behaviour verification: 15 PLAY round trips or 30 MENU presses; this was also the GUI that stopped reacting in the random soaks). S-DISPQ runs the DISPLAY loop for the message at once (`DisplayLab.task_message`, as the synchronous sends; the DISPLAY task, priority 26, outranks the GUI, 55, so on the camera it also runs before the GUI goes on). The loop handles cmd 18 (`0x501c3324`) and replies through `0x501c48bf` (D): status 0 sends {0, word 1, word 3} to the queue in the message's word 0, 6, the camera application's queue (OlyQeWr at `0x501c490c`, returning to `0x501c4913`); status 2 keeps words 0..2 at `0x62a3540c` (`0x501c4917`) and sends nothing; status 4 sends {0, kept word 1, 0} to the kept queue (OlyQeWr at `0x501c496d`, returning to `0x501c4974`). The caller `0x501c38a3` picks status 2 when `(44,sp)` equals `(0x60043286)` and status 4 when `(0x62a3540c)` is not 0 (`0x501c387f..0x501c389b`, D); the executed transitions only reply with status 0. Task 58 does not run, so S-DISPQ records a reply to queue 6 from either return address and returns E_OK; the player checks at bring-up that both return addresses follow a 7-byte call of OlyQeWr (the first version had `0x501c4971`, inside the second call, so a status-4 reply went to the kernel's queue 6 unrecorded). Called from the lab task with status 2, 4 and 0, `0x501c48bf` gives the two replies with their return addresses (X; with `0x501c4971` back, the dispq-mid-call mutant, the status-4 reply is missing). Running cmd 18 changed no frame we compared (X: the frames after the menu entry, the menu close and a PLAY press and release have the same hashes with and without it; the play session stays equal to the nav harness, which does not run it). Any other send to the DISPLAY queue is an error. A guard covers the general case: the player observes every direct call of tsnd_dtq (11 sites, byte scan) and its return; a call with timeout -1 that has not returned when a step or an idle slice ends means a full queue nobody reads, and that is an error status naming the queue (X: without S-DISPQ, the no-dispq mutant, the 30th PLAY transition gives "tsnd_dtq with timeout -1 waits on a full queue: queue 136").
