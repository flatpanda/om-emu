# The OM-5 (E144 v1.2) "5 GHz Wi-Fi hotspot" change: our own study (2026-11-12)

The third-party tool [azqeurio/om-c-firmware](https://github.com/azqeurio/om-c-firmware)
("db firmware") ships a `wifi-5ghz` feature for the OM-5 1.2 profile (E144). The
upstream om-emu study of the OM-1 (E143) version is
[`analysis/om-c-firmware/README.md`](../om-c-firmware/README.md) section 3.4; this
note is **our own, independent E144 analysis, verified against our image** —
`fw/OLY_E_144_1200_0000_0000.BIN` (92,274,688 bytes, sha256
`a0c91f3ac7caaf0925b2af609e711183cf3b5982b3333224bcef26c0c5943d11`, pinned in
`BLOBS.sha256`). Nothing is copied from om-c (the repository and release carry no
licence): their results are used as **facts and addresses only, attributed**; every
byte claim below is re-derivable from our image via `reproduce.py`.

Evidence tags as in the specs: **X** executed or measured here, **D** read from the
firmware at the cited address, **I** inference, **?** unknown. Addresses are body
offsets of the descrambled blocks; code VMA = body offset + `0x50000000`, run-time
data address = body offset + `0x60021020` (`docs/README.md` "Addresses",
`emu/src/fw/expand.mjs` — E144's main block keeps its offsets through the in-place
`olycompress` expansion). All listings/hexdumps are in `evidence/`, regenerated by
`reproduce.py` (fail-closed: pinned hashes for the vendor image, the 5 blocks, the
expanded main image, the rootfs tables, and the extracted files).

## Short answer

1. **Stock OM-5 AP channel path (RTOS, D).** `wifi_mngr_set_apl_prm` (log string
   `wifi_mngr_set_apl_prm : start`) calls the AP-channel function `0x514083fc..0x514084f4`
   (one call site, `0x514079ab`). The function reads settings 60577 (`PRM_WIFI_CHANNEL`,
   0xECA1), 625 and 497 through the getter `0x5003ea6d`; in AP mode
   (`OLNET_PRM.mode` == 2) a channel above 13 logs `ch illegal range (0-13):` and
   becomes 0; channel 0 probes card files `C:\WFCL0%03d.BIN` 1..13. The result is
   stored to `OLNET_PRM+0xcc` (`0xa272c2d4`, u16) and logged as `access point channel :`.
   The caller then sets the band byte `OLNET_PRM+0xd1` (`0xa272c2d9`) = 1 iff the
   channel is >= 35. This is the E143 mechanism at E144 addresses, byte-verified.
2. **Why stock OM-5 is 2.4 GHz only (D/I).** The RTOS clamp caps the AP channel at 13,
   so the band byte stays 0. On the A53 side the dual-band hostapd path is **stock**:
   `isc_olnet` writes `ieee80211n=1`, `ieee80211ac=1`, `wmm_enabled=1` unconditionally
   and has both `hw_mode=g` + `channel=%d` (2.4 GHz) and `hw_mode=a` +
   `vht_oper_chwidth=1` + `vht_oper_centr_freq_seg0_idx=%d` (5 GHz) branches
   (`/bin/isc_olnet`, strings `ap_conf_add_if` / `ap_conf_add_channel`). Only the
   RTOS clamp keeps the AP at 2.4 GHz.
3. **The radio (D).** `isc_olnet` loads **bcmdhd with CYW43455 firmware**:
   `/sbin/insmod /lib/modules/4.4.127/extra/bcmdhd.ko
   firmware_path=/lib/firmware/cyw43455_softap.bin nvram_path=...` — plus
   `cyw43455_sta.bin` (STA) and `cyw43455_mfg.bin` (mfg) variants, and
   `/sbin/rmmod bcmdhd` on the switch. The CYW43455 is dual-band (2.4 + 5 GHz), the
   same radio family as the OM-1 (E143). om-c's profile list is consistent: they offer
   `wifi-5ghz` for the OM-5 (E144) and withdrew it from the OM-3 (E147, CYW43439,
   2.4 GHz only — their stated reason), and the upstream note records the OM-5 II
   (E148) as CYW43439.
4. **om-c's E143 sites have clear E144 analogs (D).** On E143 om-c forces channel 36
   at two sites (12 bytes + 6 bytes, one past the range check — their data, attributed).
   On E144 the same two semantic points are: (a) the 12-byte window
   `0x51408410..0x5140841b` (the `PRM_WIFI_CHANNEL :` log call, right after the
   fetch), and (b) the clamp tail `0x51408462..0x51408464` (`clr d3; bra`) past the
   range check at `0x51408451` (`cmp 13,d1; ble`). Section 4 states a minimal
   byte-exact design; **nothing was patched, no image was produced**.
5. **The Linux side (D).** The E144 large-data block (`blk02520000`, load
   `0x42ea0000`) holds a 4.2 MB squashfs 4.0 (LZO) at body offset `0x216cfe0` with a
   **nonstandard superblock** (the `directory_table_start` field is -1; the tables were
   located empirically and pinned). `/bin/isc_olnet` (60,932 bytes, ELF32 ARM,
   mode 0755, stored in fragment 3) is the A53-side Wi-Fi service; its
   diff-relevant strings are quoted in section 5, including a **hardcoded
   `country_code=JP`** in the 2.4 GHz branch — the analog of what om-c's E143 change
   replaces with the region code from `OLNET_PRM+0x1d`.
6. **What we did NOT do (X).** No firmware or updater was executed, no camera was
   touched, no patched image was produced (OMDS-SFTY-001/002/003 all respected). The
   change of section 4 is a verified-offset, unverified-effect design (`NOT_PROVEN`
   items in section 6).

## 1. The stock OM-5 AP channel path (RTOS)

The AP-channel function `0x514083fc..0x514084f4` (249 bytes; full listing
`evidence/04_disasm_wifi.txt`, before-bytes `05_hexdump_sites.txt`):

| step | E144 address | bytes | what happens |
|---|---|---|---|
| fetch | `0x514083ff` | `fc cc a1 ec 00 00` | `mov 0xECA1,d0` — setting **60577 = `PRM_WIFI_CHANNEL`** (the id also appears in the settings dump text at body offset `0x15b137b`: `PRM_WIFI_CHANNEL,0xECA1,,,,1,FLASH`) |
| get | `0x51408408` | `dd 65 66 c3 fe c0 0c` | `call 0x5003ea6d,[a2,a3],12` — the settings getter (E143 analog: `0x500417da`); value returned in d0 |
| keep | `0x5140840f` | `83` | `mov d0,d3` — channel kept in d3 |
| log | `0x51408410` | `fc dc fc 15 53 61` `1c` `cd af 90 00 04` | 12 bytes: `mov "PRM_WIFI_CHANNEL :",a0; extbu d0; call 0x514014c6` (printf) — **om-c's E143 12-byte site A window analog** |
| param 625 | `0x5140841c` | `2c 71 02` `90 00` `04` `dd 4b 66 c3 fe c0 0c` `14` `a0 00` `c9 05` / `cc b1 00` | `mov 625,d0`; getter; `extbu d0`; `cmp 0,d0`; `bne` → mode logic, `==0` → `jmp 0x514084df` (store d3 unchanged) |
| mode | `0x51408431` | `fc a5 08 c2 72 a2` `a5 02` `c8 08` / `a5 05` `c8 47` / `ca 26` | `mov (0xa272c208),d1` — `OLNET_PRM.mode`; `cmp 2` (AP) / `cmp 5` / else |
| param 497 | `0x51408441` (AP) | `2c f1 01` `90 00` `04` `dd 26 66 c3 fe c0 0c` `83` `8d` `1d` | `mov 497,d0`; getter; `mov d0,d3; mov d3,d1; extbu d1` |
| **clamp** | `0x51408451` | `a5 0d` `c3 31` | `cmp 13,d1`; `ble 0x51408484` (≤13 passes) |
| illegal | `0x51408455` | `fc dc 0f 16 53 61` `1f` `8c` `cd 69 90 00 04` | `mov "ch illegal range (0-13):",a0` (string at data `0x6153160f`); `extbu d3; mov d3,d0`; printf |
| **zero** | `0x51408462` | `0c` `ca 21` | `clr d3` (channel := 0) ; `bra 0x51408484` — **om-c's E143 6-byte site B semantic analog** |
| join | `0x51408484` | `8d` `1d` `a5 00` `c9 57` | `mov d3,d1; extbu d1; cmp 0,d1; bne 0x514084df` (nonzero → store) |
| probe | `0x5140848a`..`0x514084c8` | — | channel == 0: memset `0xa272c4d0` (16 B), sprintf loop `C:\WFCL0%03d.BIN` for 1..13 (`0x500cc52f`, probe `0x5068b7d5`); a hit sets d3 = n; else the u16 global `0xa272c124` (`g_access_point_channel`, dumped as ` g_access_point_channel    : 0x`) overrides d3 when nonzero |
| **store** | `0x514084df` | `fc 8f d4 c2 72 a2` | `movhu d3,(0xa272c2d4)` — **`OLNET_PRM+0xcc` = channel** |
| log | `0x514084e5` | — | `access point channel :` + value; `ret [d2,d3,a2,a3],32` |

`OLNET_PRM` = **`0xa272c208`** (mode +0x00 = `0xa272c208`, country +0x1d =
`0xa272c225`, channel +0xcc = `0xa272c2d4`, band +0xd1 = `0xa272c2d9`; also +0x11c
stealth, -0xe4 `g_access_point_channel`) — the E143 struct semantics at the E144
address (all seven cell references listed in `evidence/06_olnet_prm_refs.csv`).

The **caller** (`wifi_mngr_set_apl_prm`, ~`0x51407630..0x51407abf`, log strings
`wifi_mngr_set_apl_prm : start` at data `0x615312a5` and `... : end` at
`0x61531389`) calls the channel function once at `0x514079ab`
(`call 0x514083fc,[d2,d3,a2,a3],32`) and immediately derives the band byte:

```
514079b0:  fc ac d4 c2 72 a2   movhu (0xa272c2d4),d0     ; read channel back
514079b6:  a0 23               cmp 35,d0
514079b8:  c0 06               blt 0x514079be
514079ba:  80 01               mov 1,d0
514079be:  00                   clr d0
514079bf:  fc 82 d9 c2 72 a2   movbu d0,(0xa272c2d9)     ; band = (channel >= 35)
```

— so **forcing channel 36 also sets band = 1 with no extra patch**: the band byte is
stock behavior keyed on the stored channel (D). This matches the E143 study's caller
behavior.

**Second stock writer.** `wifi_mngr_set_apl_prm_fact` (`0x51407acc..0x51407ca6`,
log strings `..._fact : start/end`) writes channel and band **without** the clamp
function: at `0x51407b62` `movhu d0,(0xa272c2d4)` with d0 = byte +101 of a parsed
record, then the same `cmp 35` → band at `0x51407b72`. This is a parallel path
(factory/test variant); which of the two paths a normal AP session takes is
**NOT_PROVEN** (section 6) — the E143 analysis saw only the main path.

**Country setter** (the `OLNET_PRM+0x1d` writer, E143 analog `0x517f067f`): validates
the region code against `0..10` (`cmp 0,a2` / `cmp 0x0a,a2; bls`, at
`0x5140862a..0x51408635`), dispatches through an 11-entry jump table at data
`0x61531e98`, and the segment shown at `0x514085ae` copies **3 bytes** (2 chars + NUL)
into `0xa272c225` (`+0x1d`) via the out-of-block memcpy helper `0x36fe001f`
(memset `0x36fe012b`), source pointer from data `0x615311ec`; a region-dependent
word is stored to `+0x20`; unknown regions log `UNKNOWN_AREA : region_code = `.
The per-region string table itself is not fully mapped (?).

## 2. Why the stock AP is 2.4 GHz only

The clamp at `0x51408451` (`cmp 13,d1; ble`) plus the `clr d3` fall-through is the
only AP-mode channel limiter: a user/menu channel above 13 becomes 0 (then the
`C:\WFCL0%03d.BIN` probe or the `g_access_point_channel` global decides), so the
stored channel never reaches 35+ and the band byte at `+0xd1` never becomes 1. On the
A53 side nothing forces 2.4 GHz: `isc_olnet`'s config builder writes
`ieee80211n=1`, `ieee80211ac=1`, `wmm_enabled=1` in `ap_conf_add_if` **stock**, and
`ap_conf_add_channel` holds both branches — `hw_mode=g` + `channel=%d` +
`ieee80211d=1` + `ieee80211h=1` + **`country_code=JP`** (2.4 GHz), and `hw_mode=a` +
`channel=%d` + `vht_oper_chwidth=1` + `vht_oper_centr_freq_seg0_idx=%d` (5 GHz,
**stock strings**). The E143 conclusion carries over byte-verified: the dual-band
hostapd path is stock; the RTOS clamp is the 2.4-only cause (D for the E144 RTOS and
isc_olnet strings, I for the causal chain).

## 3. The OM-5's radio

`isc_olnet` drives the Wi-Fi chip through **bcmdhd with CYW43455 firmware** (D,
strings of the extracted `/bin/isc_olnet`, `evidence/08_isc_olnet_strings.txt`):

- `bcmdhd` (driver name), Linux `4.4.127`, `mn-sdmmc.ko` (SDIO host);
- `/sbin/insmod /lib/modules/4.4.127/extra/bcmdhd.ko firmware_path=/lib/firmware/cyw43455_softap.bin nvram_path=...` (AP mode);
- the same with `cyw43455_sta.bin` (STA) and `cyw43455_mfg.bin` (mfg), `/sbin/rmmod bcmdhd`.

The CYW43455 is a dual-band (2.4 + 5 GHz) chip — the OM-1's radio family. This is
consistent with om-c offering `wifi-5ghz` for the OM-5 (E144) while withdrawing it
from the OM-3 (E147, CYW43439, 2.4 GHz only — their stated reason) and with the
upstream note that the OM-5 II (E148) also runs CYW43439. So 5 GHz on the OM-5's
radio is plausible at the hardware level (I; no hardware was tested — the
`cyw43455_*.bin` firmware blobs themselves are outside this updater image, section 6).

## 4. What and why we would change (design only — nothing was patched)

om-c's E143 change is two RTOS sites (12 bytes + 6 bytes, one past the range check —
their data, attributed) plus a 233-byte rewrite inside `isc_olnet` adding
`country_code=` from `OLNET_PRM+0x1d` and a 36..48 channel check (their data). The
E144 analogs, with stock before-bytes from our image:

| site | E144 window | stock bytes | role |
|---|---|---|---|
| A (force the value) | `0x51408410..0x5140841b` (12 B) | `fc dc fc 15 53 61 1c cd af 90 00 04` | the `PRM_WIFI_CHANNEL :` log call; fits e.g. `mov 36,d3 (8b 24) + mov d3,d0 (83) + extbu d0 (1c) + call print (cd af 90 00 04) + nop nop nop (cb cb cb)` — 12 bytes, log then shows 36 |
| B (defuse the clamp) | `0x51408451..0x51408454` (4 B) | `a5 0d c3 31` | `cmp 13,d1` → `cmp 36,d1` (`a5 24 c3 31`) — in-place, no layout change: 36 passes, >36 still clamps to the WFCL path |

With A + B: AP channel forced to 36, the range check passes, channel ≠ 0 so the WFCL
probe is skipped, `+0xcc` stores 36, the caller sets band `+0xd1` = 1 stock, and the
stock `isc_olnet` `hw_mode=a` branch builds the 5 GHz hostapd config
(`ieee80211ac=1`, `vht_oper_chwidth=1`). Constraints found in our image that any
patch must respect (D): the illegal-log block ends at `0x51408464` and the
`communication illegal mode` block starts at `0x51408465` (targeted by the branch at
`0x5140843f`) — writes must not cross into it; the join at `0x51408484` and the
store at `0x514084df` are shared by all modes.

Risks (analysis, not run): **regulatory** — 5 GHz channels are country-dependent;
stock `isc_olnet` writes `country_code=JP` (hardcoded) in the `hw_mode=g` branch and
has `ieee80211d=1`/`ieee80211h=1` (DFS) — the E143-style companion change feeds
`country_code=` from `OLNET_PRM+0x1d` (the E144 country setter writes that cell from
the region code); **container** — any patched block must be rescrambled with the
tail checksum recomputed so the u32 sum over head+body+tail is 0
(`docs/firmware-container.md`, `tools/olyfw.py`); the RTOS block here is scrambled
code (flags 0x0100) and the large-data block scrambled (0x0106); **A53 side** —
`isc_olnet` sits inside the squashfs (fragment 3), so its change changes the squashfs
image bytes and with them the large-data block checksum; same-length in-place edits
keep all squashfs offsets stable. Nothing of this was performed — no patched .BIN
exists (OMDS-SFTY-001/002/003 respected; `RESEARCH_ONLY`, camera-untested).

## 5. The Linux side: rootfs and isc_olnet

The large-data block `blk02520000` (45,744,064 bytes descrambled, load
`0x42ea0000`) holds a **squashfs 4.0 image at body offset `0x216cfe0`**
(4,411,689 bytes = `bytes_used`, 266 inodes, 17 fragments, 128 KiB blocks,
compression id 3 = **LZO**, mkfs 1657804150 = 2022-07-14). Its superblock is
**nonstandard**: the `directory_table_start` field (offset 0x38) is 0xFFFFFFFFFFFFFFFF
and two extra u64s follow the standard 80 bytes. The tables were located empirically
(`tools/sqfs.py locate_tables`, pinned and re-verified by `reproduce.py`):

| table | fs-relative | meta blocks (stored -> decoded) |
|---|---|---|
| inode table | `0x433db9` | 2164 B -> 8192 B, 743 B -> 2036 B |
| directory table | `0x434918` | 3098 B -> 4780 B |
| fragment entries | `0x435534` | 155 B -> 272 B (17 x 16 B) |
| fragment index | `0x4355d1` | one u64 -> `0x435534` |

Inode references are `(raw_byte_offset << 16) | payload_offset` (the root reference
`0x087607d4` names block 1's header position exactly); directory segments are
12-byte headers `{count u32, start u32 (raw inode-table offset), inode_number u32}`
followed by `{offset u16, x u16, type u16, size u16, name[size+1]}` entries (8 + name
bytes, no per-entry inode number). The root directory has 5 entries:
`bin, lib, lib32(symlink), sbin, share` — this image is the A53's **network userland
overlay** (`/sbin/hostapd`, `wpa_supplicant`, `dnsmasq`, `xtables-multi` as files;
libnl/libcurl/libisc/libolnet as libraries), not the whole root.

**`/bin/isc_olnet`**: 60,932 bytes, mode 0755, ELF32 LSB ARM (e_machine 0x28),
mtime 1657804144, stored entirely in **fragment 3** at fragment offset 44020 (no full
blocks), sha256 `618ffe3994dc85df240b4709cbd5874a3854e17edc5d5e3205444b44a38945e0`
(`evidence/11`, the .bin itself is gitignored and tracked by this hash; regenerated
by `reproduce.py`). It links against `libwpa_client.so` and `libolnet.so` and talks
to the RTOS over the ISC shared-memory channel (`olnet_uty_shm`, `RecvOLNETReqInfo`,
`ISC_OLNET_CMD_CONFIG/OPEN/START/...`). Diff-relevant strings (offsets in the
extracted file, `evidence/08_isc_olnet_strings.txt`):

- `@0049960 ol_wifi_config:I` / `@0049980`: `mode %ld secmode %ld encmode %ld ssid %s pass %s channel %d` — the config the RTOS command delivers (channel included);
- `@0055628 ap_conf_add_if:` `interface=wlan0`, `driver=nl80211`, `ctrl_interface=/var/run/hostapd`, `ieee80211n=1`, **`ieee80211ac=1`**, `wmm_enabled=1` — stock, unconditional;
- `@0055840 ap_conf_add_channel:` `hw_mode=g`, `channel=%d`, `ieee80211d=1`, `ieee80211h=1`, **`country_code=JP`** (hardcoded) — the 2.4 GHz branch; `acs_chan_bias=1:0.8 6:0.8 11:0.8`, `chanlist=1 6 11`;
- `@0055930`: `hw_mode=a`, `channel=%d`, `vht_oper_chwidth=1`, `vht_oper_centr_freq_seg0_idx=%d`, `vht_capab=[SHORT-GI-80]` — the 5 GHz branch (stock);
- `@0052720`: `freq=`, `freq=%d`, `band_type = %d`, `[0].band_type = %d`, `ap_channel = %d`, `scan_freq=%d`, `freq_list=%d` — the band/channel plumbing;
- `@0049872 ol_wifi_nvram_country_set` — an existing country setter;
- `/sbin/insmod .../bcmdhd.ko firmware_path=/lib/firmware/cyw43455_{softap,sta,mfg}.bin ...`, `/sbin/rmmod bcmdhd` — the radio (section 3);
- `/etc/hostapd.conf`, `hostapd -B -P %s %s` — the generated config file (E143: om-c leaves it unchanged).

The om-c E143 Linux change (233 bytes: `country_code=` from `OLNET_PRM+0x1d` + a
36..48 channel check — their data) lands on E144 in these same functions
(`ol_wifi_config` / `ap_conf_add_channel` / the band branch); the exact E144 byte
diff is theirs and is not reproduced here.

## 6. Explicit NOT_PROVEN / UNRESOLVED

- **No execution.** Everything above is static byte reading (D). The clamp/branch
  behavior was not run in the emulator (the om-emu lab runs E143 natively; E144 ports
  exist in the survey but were not driven here), and no camera was involved. om-c's
  camera reports are their claims, not evidence.
- **The minimal design of section 4 is unverified at runtime** — offsets and stock
  bytes are verified, the resulting behavior is not. In particular the side effects of
  writing the log window (site A) and of `cmp 36` (site B) on the remaining modes
  (`communication illegal mode` path) were not executed.
- **isc_olnet's ARM code was not disassembled.** Whether stock E144 `isc_olnet`
  clamps/rejects the channel (the analog of om-c's 36..48 check), and exactly how
  `band_type` selects the `hw_mode=a` branch, is UNRESOLVED; the strings prove the
  functions and format strings exist, not the branch conditions.
- **The A53 base system is outside this image.** The squashfs overlay has no
  `/etc`, `/usr` or `/lib/firmware`; the `cyw43455_*.bin` firmware blobs and
  `/etc/hostapd.conf`'s runtime form are not in the studied blocks (bounded absence:
  only the insmod path strings prove the names). What the A53 boots from is a
  separate question.
- **Country handling.** The region-code → country-string table (region 0..10) is not
  fully mapped; only one segment's 3-byte memcpy into `+0x1d` is shown. What
  `country_code=` the 5 GHz branch writes (none of the branch's strings says) and
  whether `ol_wifi_nvram_country_set` feeds hostapd is UNRESOLVED — regulatory risk
  for a real 5 GHz AP.
- **`wifi_mngr_set_apl_prm_fact`** (second writer) is stock and unclamped; which
  path a real AP session takes is NOT_PROVEN. `mode` value 5 and the
  `communication illegal mode` semantics are undetermined.
- **`g_access_point_channel`** (`0xa272c124`): cleared at `set_apl_prm` start
  (`0x51407630`), read by the channel function, printed by the dump — the writer of a
  nonzero value was not located (it may be fed by the WFCL files).
- **Reader limitations.** The tree walk stops at one entry whose inode offset
  (8191) cannot parse inside an 8192-byte metadata block — one directory of the
  overlay is not fully walked; the `x` u16 in dir entries is unparsed; the
  `BCS\0` table rows are documented but not load-bearing.
- The exact om-c E144 patch bytes are not reproduced (their `profiles.json`; no
  licence — facts and addresses only, per the upstream study's rule).

## 7. Provenance, method, commands

- Image: `fw/OLY_E_144_1200_0000_0000.BIN` (sha256 `a0c91f3a…`, = `BLOBS.sha256`
  line 31). All 5 blocks re-unpacked and descrambled with `tools/olyfw.py --dump`
  and re-verified against `BLOBS.sha256` by `reproduce.py` (block sha256s pinned in
  `input_manifest.csv`).
- Main block run-time image: in-place LZ4 expansion of the two `olycompress`
  containers (`0x825fe0`: 2,254,189 → 4,683,776 B; `0xc9d7e0`: 2,697,821 → 6,836,224 B;
  11,520,000 raw bytes total, matching the survey's "about 11.5 MB"); expanded image
  sha256 `692f1b9e…` (pinned).
- Disassembly: `tools/mn103dis.py`, written for this study from
  `docs/mn10300-isa-spec.md` section 3 (complete base opcode map) with the
  source/dst bit order cross-checked against `emu/src/core/cpu.mjs` (`src = op>>2&3,
  dst = op&3`); MOVM/CALL/RET mask bits `d0,d1,a0,a1,d2,d3,a2,a3`. The pinned
  `tools/mn10300-objdump` binary is not present on this Windows host — the Python
  disassembler was used for everything; six windows disassemble with **zero**
  undecoded slots (`evidence/04`).
- Rootfs: `tools/sqfs.py` — pure-stdlib squashfs 4.0 + LZO1X reader written for this
  study (algorithm of Linux `lib/lzo/lzo1x_decompress_safe.c`, GPL-2.0, reimplemented;
  two empirical pins: squashfs metadata blocks are byte-packed without alignment, and
  the LZO **`M2_MAX_OFFSET` is 0x800** — with 0x400 three of five blocks still match
  but fragment 3 diverges; 0x800 byte-matches python-lzo 1.15 on all five pinned
